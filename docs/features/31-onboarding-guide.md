# 31. 初期設定の導線と使い方ガイド

対象: 発行者（ホスト）　状態: 実装済み（#353・2026-08-27）

## これは何か

登録直後の「何をすれば動き出すのか分からない」を解く2つの導線。

1. **初期設定カード** — ダッシュボード上部に出る3ステップのチェックリスト（進捗つき）
2. **使い方ガイド** — ヘッダーの「使い方ガイド」から開く、左右に送る紙芝居形式のModal

## なぜ必要か

「初期設定の方法がわかりにくい」というユーザーからの指摘。登録直後のダッシュボードは
「今日の予定（空）」「予約ページを共有（まだ無い）」「要対応」が並ぶだけで、**最初に何を
すればサービスが動き出すのか**が画面から読み取れなかった。

実際に詰まる順番は決まっている。カレンダーが未連携だと空き枠が正しく出ず、予約ページが
無ければ共有するURLも無い。この「使えない理由」が画面のどこにも出ていなかった。

並べる順は「カレンダー連携 → プロフィール → 予約ページ」。予約ページを作った時点で共有できる
URLが発行される＝人を招ける状態になるので、それより前にプロフィールを埋めてもらう。

## 1. 初期設定カード（ダッシュボード）

| ステップ | 完了の判定 | 導線 |
|---|---|---|
| ① Googleカレンダーと連携する | `/api/me` の `calendar_connected` | `/api/google-auth-start?connect=1`（設定画面を挟まず直接） |
| ② プロフィールを設定する | `/api/profile` の基本7項目がすべて埋まっている | `/profile.html` |
| ③ 予約ページを作る | `/api/booking-pages` の件数 ≥ 1 | `/booking-settings.html?new=1` |

### 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 達成状況の取得 | **既存の取得を使い回す**（新しいAPIを足さない） | ダッシュボードは既に `me` / `booking-pages` / `profile` を叩いている。カードのために往復を増やさない |
| 判定できないとき | **カードごと出さない**（3つとも判明するまで `hidden`） | 取得に失敗した項目を「未完了」と決めつけると、連携済みの人に「連携する」と出してしまう |
| 強調 | **次にやる1つだけ**を朱のボタンにする | 3つとも同じ強さで並ぶと、どれから手を付けるか分からない |
| ②の基準 | 「要対応」の**プロフィール未設定**と同じ（7項目すべて） | 2か所で基準が違うと「完了なのに要対応に出る」が起きる |
| 並び順 | 連携 → プロフィール → **予約ページを最後**（2026-08-31 に②③を入れ替え） | 予約ページは作った時点で共有URLが出る＝人を招ける状態になる。先にプロフィールが埋まっていれば、最初に案内したURLから相手が見る情報が欠けない |
| 完了後 | 完了の行を出し、「閉じる」で以後は出さない（`localStorage: kimaru.setupDone`） | 済んだ人の画面を毎回占有しない。連携解除などで未完了に戻ったら再び出す |
| 保存先 | localStorage（DB列を足さない） | 端末ごとの表示の好みでしかなく、サーバに持つ理由がない |

## 2. 使い方ガイド（機能一覧ページ＋項目ごとの説明Modal）

ヘッダーの「使い方ガイド」は **`/guide.html`（機能一覧）** へ送る。一覧は**項目名だけのボタン**で、
押すとその項目**だけ**の説明Modalが開く。**送りは1項目の中のページ間だけで、項目をまたがない。**
現在15項目・27ページ。

| 章 | 項目（括弧内＝Modalのページ数） |
|---|---|
| 概要 | キマルとは／予約ページとは |
| 予約受付の準備 | Googleカレンダーの連携（2）／Zoomの連携（2）／**予約ページの作成方法（7）**／プロフィールの設定（2） |
| 案内から面談当日まで | 予約ページの共有方法／ピンポイント日程調整（2）／予約確定後の流れ／アンケート回答の確認方法／キャンセル・日程変更への対応／予約の受付を一時的に止める |
| 継続的な利用 | 相手管理とは／相手管理の使い方／プランごとの機能の差異（3） |

**「予約ページの作成方法」は予約ページ設定の画面ぶんをまとめた7ページ**で、画面で上から順に触る順に並べる。

| ページ | 中身 |
|---|---|
| 1 作成の手順 | 作成 → 名称 → 時間設定 → 受付時間 → 保存してURL発行 |
| 2 基本の欄 | 予約ページ名・公開URL・説明文・受付状態 |
| 3 面談の条件 | 予約時間・開催方法・開催場所/電話案内/URL |
| 4 受付時間 | 曜日ごとの受付時間 |
| 5 前後バッファ | 前後に空ける時間とバッファ予定名 |
| 6 候補の出し方 | 公開範囲・何時間後から・表示間隔 |
| 7 事前アンケート | 質問の追加と回答形式 |

### 説明の中身は項目ごとに形が違う

読み手が知りたいことは項目ごとに違うので、`guide.js` の `ENTRIES` でページごとに部品を選ぶ。

| 部品 | 使う場面 |
|---|---|
| `lead` | 全ページ。1段落の要約 |
| `points` | 「〜とは」の概要。順序のない箇条書き |
| `steps` | 「〜の連携方法」「〜の作成方法」。順序のある手順 |
| `fields` | 「〜の設定項目」。欄の名前と説明の対 |
| `note` | 上限・できないこと・元に戻せないこと |

文言のキーは **単ページ = `guide.<key>.*`／複数ページ = `guide.<key>.p<n>.*`**。この2つの規則は
`guide.js` の `pagesOf` / `prefixOf` に閉じ込めてあり、`scripts/test/unit.mjs` も同じ関数の出力
（`window.KimaruGuide.entries[].pages[].prefix`）を通して必要なキーを組み立てるので、規則は1か所にしかない。

### 1ページぶんの分量（iPhone 12 でスクロールなし）

**1ページは、iPhone 12（390×664＝Safariのツールバーが出ている状態）でスクロールせずに収まる量に抑える。**
`scripts/test/e2e.mjs` が全ページの `scrollHeight` を実測して固定しているので、超えるとテストが落ちる。

**収まらなくなったら、文を削るのではなくページを足す。** 手順や設定項目を削ると「その説明を読んでも設定できない」
状態に戻るため。一覧のボタンは増やさない（similar な名前のボタンが並ぶと、目的の説明を探しにくい）。

### 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 入口 | ヘッダーからは**まず一覧へ**（Modalを直接開かない） | 「予約ページの作り方だけ知りたい」人が、通しの紙芝居を送り続けることになるため |
| 送りの範囲 | **1項目の中のページ間だけ。項目をまたがない** | 全項目を通しで送れると、どの項目を押しても同じ器が開いて「どこまでがこの説明か」が分からない。次の項目は一覧に戻って選ぶ |
| 分量が多い項目 | **1つのボタン＋複数ページ**（ボタンを分けない） | 「予約ページの設定項目（基本）／（面談の条件）／（候補の出し方）」のように似た名前のボタンが並ぶと、一覧から目的の説明を選べない |
| 単ページの項目 | 送りのボタン自体を出さない | 押しても何も起きないボタンを置かない。←/→ も単ページでは効かせない |
| 見出しの出し分け | 複数ページ＝上のラベルに項目名・見出しにページ名／単ページ＝上のラベルに章名・見出しに項目名 | 見出しが項目名のままだと、送っても同じ画面に見える |
| 説明の粒度 | **「〜とは（概要）」と「〜の方法（手順）」は別の項目** | 1項目に概要と手順を同居させると、知りたいほうに辿り着くまで読み飛ばすことになる |
| 説明の型 | **ページごとに部品を選ぶ**（全項目を同じ型で書かない） | 当初は全項目が「図＋利用場面＋3ステップ」だったが、それでは「Zoomはどう連携するのか」「この欄は何を意味するのか」に答えられなかった |
| 1ページの分量 | **iPhone 12（390×664）でスクロールなし**。超えたらページを足す | 開いた瞬間に全体が見えないと、手順書として読み通せない |
| 一覧の見せ方 | **項目名だけのボタン**（要約も図も出さない） | 1件あたりを短くして一覧性を優先する |
| 1つの画面の説明 | **その画面で設定する項目は1つのModalにまとめる** | 「予約ページ設定」の画面を開いたまま読み進められる。受付時間・前後バッファ・事前アンケートを別ボタンにすると、同じ画面の話が一覧に散らばる |
| ボタンの見た目 | 1pxの枠＋角丸6px、**下辺だけ3pxで立体に見せる**（影は使わない） | 押せることを見た目で示す。押したときは下辺を1pxに戻して同じぶん下げる（沈む動きになり、高さは変わらない）。影を足すと `--shadow` を使う既存のカードと区別がつかなくなる |
| 図 | **持たない** | 項目が「機能」から「操作」に細かくなったことで、図が手順の言い換えにしかならなくなった（`.s-*` のCSSと骨格SVGの生成コードは削除） |
| 置き場所 | **`/guide.html` だけが `guide.js` を読む** | 開く先が一覧1枚に決まったので、全ページに配る必要がなくなった（当初は `usage.js` と同じく Edge Function が全HTMLに注入していた） |
| 一覧の中身 | `guide.js` の `ENTRIES` / `GROUPS` に持ち、HTMLには項目名を書かない | 項目名を2か所に持つと、説明を1つ足したときに必ず片方が古くなる。`group` の書き忘れと、部品を1つも持たないページは `scripts/test/unit.mjs` が落とす |
| ログインの要否 | **不要**（`PROTECTED_PATHS` に入れない） | 中身は操作の説明だけで、ユーザーのデータを含まない。登録前に「何ができるのか」を読めるほうがよい |
| 直リンク | 開いている項目を URL の `#key` に載せる（ページ番号は載せない） | 案内したいのは説明の単位で、その何ページ目かではない |
| 文言の置き場所 | i18n.js（`guide.*` キー・3言語） | 3言語の対称性を既存のテストで担保できる |
| 文体 | **公的な手引き・外部資料に準じた です・ます調** | 当初の語りかけ調は「機械が書いた文章」という印象を与えた。条件は「〜する場合」、動作は「〜します／〜できます」。初期設定カードも同じ文体 |
| ナビの折り返し | ログイン時だけ**ハンバーガーの境界を1180pxに広げる** | ナビが10項目になり、1180px 未満では言語選択とアバターが2段目に落ちてヘッダーからはみ出す |

### CSSの注意

スマホ用の詰め（`@media(max-width:620px)`）は **`.guide` 系の指定より後ろに置くこと**。
同じ詳細度なので、前に置くと base に上書きされて黙って効かなくなる（実際に一度そうなり、
高さの実測が通っているのに端末では詰まっていない、という状態になった）。

## 残る穴

- どの機能を開いたか・どの枚で離脱したかは計測していない（`page_events` の `event` は
  `page_view` / `limit_hit` の許可リスト制。増やすならサーバ側の許可リストも触る必要がある）。
  一覧ページ自体の表示回数は `/guide.html` の `page_view` として残る。
- 一覧に検索・絞り込みは無い（15項目・4章なのでスクロールで足りる）。これ以上増えるなら検索を足すかを決め直す。
- 説明はすべて手書きで、画面の実装とは自動で同期しない（例: `bs.*` の文言を変えても `guide.page-settings.*` は変わらない）。
  設定項目を増減したときは、この2つを合わせて直すこと。
- ステップ③は「予約ページが1枚でもある」だけを見ており、受付時間が空のままでも完了になる。
