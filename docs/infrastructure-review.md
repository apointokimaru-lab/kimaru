## 2. 判断が分かれた点：DB は **Supabase を正式採用**

仕様書は RDS for PostgreSQL を推奨しているが、**現行の Supabase（PostgreSQL）を継続**する。

**これは暫定措置ではなく正式採用**とする。「いずれ RDS へ移す」と決めつけない。性能・セキュリティ・費用の条件を満たす限り継続してよい。移行は下記の再評価トリガーが成立した時点で判断する。

### 先に撤回する論拠

「移行リスクが大きいから継続」は**この規模では成り立たない**。本番は予約93件・オーナー数十件規模で、`pg_dump`/`restore` で完了する。移行の技術的難度は低い。

### 継続する理由

**(1) 並行稼働がそのまま可能になる（最大の理由）**

新旧アプリが同じ DB を参照できるため、画面・機能単位で順に切り替えられ、問題が出れば戻せる。
RDS へ同時に移すと**アプリ移行と DB 移行を同時に行う**ことになり、障害時に原因を切り分けにくい。

```text
現行アプリ ＋ Supabase
    ↓
新アプリ ＋ Supabase（並行稼働）
    ↓
新アプリへカットオーバー
    ↓
安定稼働
    ↓
必要性が出た時点で RDS を再検討
```

**(2) PoC の AWS 構成を単純化できる**

DB が VPC 外なら、**プライベートデータサブネット・NAT Gateway・VPCエンドポイントを PoC で建てずに済む**。

**(3) 後から移す選択肢が安く残る**

データ規模が小さい＝いつ移しても安い。今移す緊急性がない。

### RDS へ移す再評価トリガー

- 法人契約で「VPC 内完結」「AWS 内でのデータ保持」を要求された
- Bot／ワーカーからの接続レイテンシが**実測で**問題になった
- Supabase のプラン費用が RDS 相当構成を上回った
- 監査要件で CloudWatch / IAM への統一が必要になった

### 接続方式は用途で分ける

| 処理 | 接続方式 |
|---|---|
| API・短い CRUD | Supavisor **transaction mode** |
| Bot の短い状態更新 | transaction mode |
| マイグレーション | **direct または session mode** |
| `pg_dump` / `restore` | direct または session mode |
| 長時間トランザクション | direct または session mode |
| session-level advisory lock | **使用しない**（5章） |

- Fargate タスクは増減するため、直結でコネクションを食い潰さないこと。
- **transaction mode では prepared statement の扱いに制約がある**。Drizzle のドライバー設定と PostgreSQL クライアントの組み合わせを**実機で確認**する（PoC の第1週タスク）。

### 移行前に確認すること（費用比較に含める）

仕様書16は「日次バックアップ・PITR・7〜30日保持・月1回の復元試験」を求めている。**Supabase の PITR は上位プラン／有料アドオン**なので、要件を満たすプラン費用を確認し、RDS 相当構成との比較に含める。ここを外すと「安いから継続」の判断が崩れる。

## 3. PoC で削るもの（固定費と運用対象）

仕様書 Stage 1 の月額目安は 3万〜10万円。**PoC は運営者限定（同時Bot 1〜3）**であり、先行100名でも売上は月 ¥98,000 なので、この段階の固定費は絞る。

| 仕様書の構成 | PoC での提案 | 理由 |
|---|---|---|
| ElastiCache (Valkey/Redis) | **入れない**。同時実行制御は5章の方式 | 仕様書自身が「Redis は正本キューにしない／役割はロック・カウンタ・レート制限」としている。同時Bot 10以下ならその役割は DB で足りる |
| NAT Gateway＋プライベートサブネット | **パブリックIP付き Fargate** | Bot はどのみち外向き通信が必要。NAT は固定費＋データ処理料が効く |
| ALB | **置かない**（下記のとおり理由を正確に） | |
| GPU ワーカー（STT） | **CPU の faster-whisper と外部API を並列比較** | 6章 |
| RDS Multi-AZ | Stage 3 以降 | |

### ALB を置かない理由（記述の訂正）

「API が1タスクだから不要」ではなく、**PoC では公開 API を新設せず、現行 API から AWS サービス（SQS・Scheduler・S3）を操作するため不要**、が正確。

新しい API を Fargate へ移した時点で、**ALB / API Gateway / CloudFront＋Lambda のいずれかが必要**になる。ここを「後で足す」前提として明示しておく。

### パブリックIP付き Fargate のセキュリティ条件

- インバウンドルールなし（アウトバウンドのみ許可）
- コンテナへ SSH 不可・**ECS Exec は通常無効**
- Bot ごとに短期認証情報のみ渡す
- ログは CloudWatch へ送出

### 最初から入れる（後付けが高い）

SQS＋DLQ／EventBridge Scheduler／S3／ECR／Secrets Manager／Terraform／構造化ログ＋Sentry／`tenant_id`／マイグレーション／**主要な外部依存のインターフェース設計**（STT・LLM・Queue・Storage・同時実行制御）。

## 4. 同時実行制御（初版の記述を修正）

> **初版の誤り**: 「同時実行制御は Postgres の advisory lock で代替」とだけ書いていた。
> **Supavisor の transaction pooling ではリクエスト間で同じ物理接続が保証されない**ため、セッションレベルの `pg_advisory_lock` は成立しない（セッション終了まで保持される前提が崩れる）。**セッションレベルのロックは使わない。**

### 用途ごとの方式

| 制御対象 | PoC での方式 |
|---|---|
| 短い DB 処理の排他 | **`pg_try_advisory_xact_lock()` を同一トランザクション内で**使う（トランザクション終了で自動解放） |
| 二重 Bot 起動の防止 | **DB の一意制約** |
| 1ユーザー1Bot（120分の長時間） | **`bot_leases` テーブルによるリース方式**（DB 接続を保持しない） |
| ジョブの重複防止 | SQS メッセージ＋**DB の冪等キー** |

### `bot_leases`

```text
bot_leases
- lease_key        （例: tenant_id + user_id）
- tenant_id
- user_id
- meeting_id
- acquired_at
- expires_at
- heartbeat_at
- status
```

- 取得は一意制約で原子的に行う（`INSERT ... ON CONFLICT DO NOTHING`）
- Bot 稼働中は定期的に `heartbeat_at` を更新する
- `expires_at` は「最大会議時間＋余裕」で設定し、**期限切れリースを回収するクリーンアップジョブ**を回す
- Bot がクラッシュしてもリースが残り続けないこと（回収されること）を PoC で確認する

### 補足：SQS メッセージの寿命に Bot 実行を紐づけない

Bot は ECS タスクとして最大120分動くが、**その間 SQS メッセージを保持しない**。オーケストレーターは `RunTask` を発行した時点でメッセージを削除し、以降の Bot の状態はイベント（`bot.joined` / `bot.completed` 等）で受け取る。可視性タイムアウトを会議時間に合わせる設計にはしない。

### インターフェースを最初から切る

Redis を後から入れられるよう、実装は抽象越しに呼ぶ。

```ts
interface ConcurrencyLimiter {
  acquire(key: string, ttlSeconds: number): Promise<boolean>;
  heartbeat(key: string, ttlSeconds: number): Promise<void>;
  release(key: string): Promise<void>;
}
```

PoC は PostgreSQL 実装、拡大時に Redis 実装へ差し替える。

### Redis を入れる条件

同時Bot 数十以上／高頻度のレート制限が必要／DB への同時接続制御が負荷になった／分散キャッシュが必要／リアルタイム状態表示が増えた。

## 5. 原価（**目標値**であり仕様値ではない）

### 前提となるプラン（2026-08-06 変更）

| プラン | 現在 | 有料会員100名到達後 | Bot 利用枠 |
|---|---:|---:|---:|
| Pro | ¥980 | **¥2,200** | 月 **5時間** |
| プレミアム | ¥2,200 | **¥4,800** | 月 **20時間** |
| マスター（Bot 稼働後に追加） | — | **未定** | 月 **100時間** |

### 1時間あたりの目標原価

| 項目 | 1時間あたり目標 |
|---|---:|
| Bot コンテナ（2vCPU / 2〜4GB） | ¥3〜15 |
| 文字起こし：外部API（Whisper系） | ¥40〜60 |
| 文字起こし：自前 CPU バッチ | ¥3〜10 |
| AI要約ほか（Queue/Scheduler/ログ含む） | 数円 |

> これらは**目標値**であって確定値ではない。CPU 原価はインスタンスタイプ・モデル・vCPU 数・beam size・VAD・音声分割方法・同時処理数・モデルのロード時間で大きく変わる。**PoC の実測でのみ確定する。**

### プラン別の原価試算（枠を使い切った最悪ケース）

前提: 文字起こし 外部API ¥50/h・自前CPU ¥6/h、Bot ¥10/h、要約ほか ¥5/h、**正常完了率90%**（実効原価 ＝ ÷0.9）。

| プラン | 枠 | 外部API方式の実効原価 | 自前CPU方式の実効原価 | 価格 | 判定 |
|---|---:|---:|---:|---:|---|
| Pro | 5h | 約 **¥360** | 約 **¥120** | ¥2,200 | **どちらでも成立** |
| プレミアム | 20h | 約 **¥1,440** | 約 **¥470** | ¥4,800 | **どちらでも成立** |
| マスター | 100h | 約 **¥7,200** | 約 **¥2,330** | 未定 | **文字起こし方式が価格を決める** |

**結論が初版から変わった点**

- 枠が月30時間から **5h / 20h** に縮小されたことで、**Pro とプレミアムは外部API方式でも成立する**。初版の「外部APIでは赤字」という結論はこの2プランには当てはまらない。
- 一方 **マスター（100時間）は文字起こし方式で原価が3倍以上変わる**。外部API方式なら原価だけで約¥7,200 なので、粗利を確保するには相応の価格設定が必要になる。自前CPUが成立すれば大幅に下げられる。
- したがって **PoC で自前CPUを測る意味は「Pro/プレミアムの黒字化」ではなく「マスタープランの価格決定」に移った**。優先度は下がっていない。
- 実利用率を掛ければ平均原価は下がるが、**枠の設計は使い切られる前提（最悪ケース）で行う**。

### 総原価の式

```text
1会議時間あたり総原価
  = Bot 実行費
  + 音声一時保存
  + 文字起こし
  + AI要約
  + SQS / Scheduler / ログ
  + 失敗再処理費
```

**忘れやすいのは失敗分**。

```text
実効原価 = 正常処理原価 ÷ 正常完了率
```

正常完了率90%なら、100時間分の議事録を届けるのに約111時間分の処理費がかかる。**提供時間枠の設計はこの実効原価で行う。**

### 含意

- Bot のコンテナ代より**文字起こしが支配的**。仕様書の「Bot原価15円/時間以下」を達成しても、文字起こしが合わなければ意味がない。
- **マスタープランの価格は実測原価が出るまで確定しない。**
- Pro・プレミアムの枠（5h / 20h）は原価面では余裕があるので、**枠を広げる余地があるかは実測後に再検討**できる。

### PoC では API と CPU を「並列比較」する

初版では「まず API で作って、合わなければ CPU に差し替える」としたが、**API 実装だけ先に本番へ入れるとその仕様に依存しやすい**。PoC では同じ音声で並列に測る。

| パターン | 目的 |
|---|---|
| small / int8 / CPU | 最安候補 |
| medium / int8 / CPU | 品質とのバランス |
| large-v3-turbo / int8 / CPU | CPU で成立するか |
| GPU | 高速化時の原価 |
| 外部API | 初期フォールバック |

### 計測記録テンプレート

```text
音声時間：60分
モデル：
CPU（インスタンスタイプ）：
vCPU / メモリ：
処理時間：
実行料金：
日本語品質：
固有名詞の誤り数：
話者分離：
```

**品質評価の手順を先に決める。** 同じ音声（できれば実際の面談録音）に対し、**固有名詞リストを用意して誤り数を数える**。これを決めずに測ると「品質」が比較不能になる。

## 6. 既存本番からの引き継ぎ

仕様書は「これから作るもの」の設計としては十分だが、**稼働中の本番から移る**視点が入っていない。ここを落とすと外部サービスの再申請・再設定が発生する。

| 対象 | 制約 |
|---|---|
| セッションCookie `kimaru_session` | **Cookie 仕様一式と秘密鍵を完全互換で移植すれば、再ログインを回避できる**（下記に現行仕様） |
| Google OAuth redirect URI・スコープ | 変更により**再審査・再検証が必要になる可能性がある**ため、既存設定を維持する（2026-07-11 に `calendar.events` 承認済み） |
| Zoom OAuth redirect URI・スコープ | 同上。**現在審査中**のため、Bot 用スコープを足す時期に注意 |
| 予約ページURL `/b/{slug}`・公開プロフィール `/u/{slug}` | 顧客に配布済み。**変更不可** |
| 予約管理リンク `/manage-booking.html?k=<id>.<token>` | 送信済みメールに残る。**旧形式 `?id=&t=` も受け続ける** |
| Square Webhook 受信URL・署名鍵 | 落とすと課金の付与が止まる |
| Resend Webhook（バウンス・苦情の自動サプレッション） | 落とすと配信品質が劣化。`email_suppressions` の移行漏れは法的リスク |
| MCP `/.well-known/*`・`/api/mcp`（OAuth 2.1） | プレミアムの接続が切れる |
| `google_connections` / `zoom_connections` の暗号化トークン | `TOKEN_ENCRYPTION_KEY` の引き継ぎ方針が必要。鍵を変えるなら再暗号化バッチを用意する |

### 現行セッションCookieの完全仕様（新スタックで再現する）

`netlify/functions/_lib/crypto.js` の実装。**Cookie 名と `SESSION_SECRET` だけでは不十分**で、以下すべてが一致して初めて再ログインを回避できる。

```text
Set-Cookie: kimaru_session=<payload>.<signature>; Path=/; HttpOnly; SameSite=Lax; Secure; Max-Age=2592000

payload    = base64url(JSON.stringify({ ownerId, ts }))   ※キーの順序も含めて同一にする
signature  = base64url(HMAC-SHA256(SESSION_SECRET, payload))
Domain     属性なし＝host-only（kimaru-co.jp）
検証       署名を定数時間比較し、さらに ts が 30日以内かつ未来すぎないことを確認
別系統     運営用 kimaru_admin_session が別に存在する（混同しない）
```

移行前に**旧実装が発行した Cookie を新実装で検証できること**をテストで確認する（逆方向も）。

### 追加の確認項目

| 対象 | 確認事項 |
|---|---|
| Cookie | Domain・Path・Secure・SameSite・有効期限・署名形式・payload 形式 |
| HMAC | 旧・新双方で署名検証テスト（相互運用） |
| 時刻 | DB は UTC、UI は JST |
| Cron・予約処理 | 旧新で**二重実行されない**こと（リマインダーが2通行かない） |
| メール | Message-ID・冪等キーによる重複防止 |
| Webhook | 同じイベントを旧新双方で処理しない |
| OAuth state | 新旧で衝突しない |
| CSP・CORS | 新ドメインを許可 |
| DNS TTL | 切替前に短縮 |
| Secrets | 移行後のローテーション計画 |
| Square | Webhook イベントの再送試験 |
| Resend | バウンス・苦情の移行試験 |

## 7. 同一DBでの並行稼働ルール（新設）

「同じ Supabase を参照する」は移行を簡単にするが、**旧新が自由に同じテーブルへ書くと壊れる**。次を必須ルールとする。

### Expand – Migrate – Contract

| フェーズ | 内容 |
|---|---|
| **Expand** | 既存を壊さず、新しいカラム・テーブルだけ追加する。**NULL 許容・デフォルト値あり**。旧コードから見ても問題ない状態 |
| **Migrate** | 新旧が共存しながらデータを移す |
| **Contract** | 旧アプリ停止後に、不要カラム・旧仕様を削除する |

### 並行稼働中の禁止事項

- カラム名の変更
- カラムの削除
- 型の変更
- NOT NULL の即時追加
- 旧コードが知らない enum 値の投入
- 既存 API レスポンスの破壊的変更

### 書き込み責任を「データ領域単位」で一つに決める

画面単位ではなくデータ単位で決める。**同一レコードを旧新双方が更新する二重書き込みは避ける。**

| データ | 書き込み担当 |
|---|---|
| 予約 | 旧または新の**どちらか一方**（切替時点を決める） |
| 顧客 | 移行期間中の責任を明記する |
| タスク | 新システムのみ |
| Bot・会議 | 新システムのみ |
| 文字起こし・要約 | 新システムのみ |
| 課金 | **切替完了まで旧システム** |

### `tenant_id` の入れ方

新スタックは全業務テーブルに `tenant_id` を要求するが、現行は `owners` 単位の単一モデル。**Expand フェーズで既存テーブルに `tenant_id` を NULL 許容で追加**し、当面は owner と 1:1 で埋める。テナント＝オーナーのままにするか、`tenants` テーブルを新設して owner を紐づけるかは、法人対応の設計時に決める（未決定 #16）。

## 8. 移行方式：機能単位の Strangler Fig パターン

```text
旧システムを残す
   ↓
新機能を新システムへ実装
   ↓
経路を少しずつ新へ移す
   ↓
旧機能を停止
```

### カットオーバー順（安全な順）

1. 読み取り専用画面
2. 顧客一覧
3. タスク管理
4. 新規予約作成
5. 予約変更・キャンセル
6. 通知
7. OAuth
8. 課金
9. MCP
10. 旧システム停止

**決済と OAuth は最後**にする。失敗時の影響が最も大きく、切り戻しも重いため。

**本番データのコピーで移行リハーサルを最低1回**行ってから本番切り替えを実施する。

### 完了条件

- 6章の表の項目がすべて新スタックで機能する（実機確認）
- 予約 → 確認メール → リマインド → キャンセル／変更の一連が通る
- ロールバック手順が用意されている

## 9. EventBridge Scheduler の運用ルール

会議ごとに一回限りのスケジュールを作る前提で、次を決めておく。

| 項目 | 決め |
|---|---|
| 名前規則 | `meeting-{meeting_id}-bot-start` |
| スケジュールグループ | 環境別に分ける（staging / production） |
| 実行後 | 自動削除（`ActionAfterCompletion`） |
| 会議時間の変更 | 既存スケジュールを**更新** |
| キャンセル | スケジュールを**削除** |
| 二重登録防止 | `meeting_id` を一意キーにする |
| 失敗時 | DLQ へ |
| タイムゾーン | **開始時刻は UTC で保存**し、明示的に渡す |
| 柔軟な時間枠 | **OFF**（会議開始に対して遅延させない） |
| 冪等キー | Bot 起動ジョブに付与する |
