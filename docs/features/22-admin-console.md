# 22. 運営管理ページ（運営コンソール）

[← 機能一覧に戻る](./README.md)

- ステータス: ✅ 実装済（運営ログイン `/operator-login.html` ＋ 運営セッション、運営コンソール、運営者管理 `/operators.html`、分析ダッシュボード `/analytics.html`）。本文ドラフト等の周辺は別タスク
- 対象: **運営（運営者）専用**
- 仕様: [`../spec.md`](../spec.md) 主要機能 9（Cat Key 不正対策）

## 概要

運営（サービス提供側）が利用者全体を把握・管理するための画面。**発行者ユーザーが使う「相手管理（[14](./14-customer-management.md)）」とは別物**で、運営だけがアクセスする。

> 打ち合わせ（2026-06-03）で管理画面は2系統あると整理:
> - **ユーザー向け管理**: プロフィール編集（[17](./17-profile.md)）・質問設定（[10](./10-questionnaire.md)）・相手管理（[14](./14-customer-management.md)）。`dashboard.html`（ハブ）/ `contacts.html`（相手管理）/ `profile.html` / `booking-settings.html`。
> - **運営者向け管理**（＝本ドキュメント）: 全ユーザー一覧と、Cat Key の承認・強制降格など。

## 仕様詳細（運営が触る機能）

1. **ユーザー一覧**
   - 全登録ユーザーを一覧表示（名前・メール・プラン・登録経路・Cat Key 利用有無など）。
   - 名前で本人確認できる（運営は名前で「この人おかしい」と気づける、という前提）。
2. **Cat Key 承認制**（[19](./19-cat-key-admin.md) と連動。決定 2026-06-03）
   - Cat Key 入力者を即時付与せず、**運営コンソールの画面から「承認」ボタンを押下**して有効化する。
   - フロー: ユーザーが Cat Key 入力 → **承認待ち**として記録 → 運営が一覧で確認 → 承認（または却下）→ 有料機能を無料で解放。
   - 承認待ち・承認済み・却下の状態を一覧で管理。
3. **プラン強制操作（有料 → 無料への変更）** ★運営の中核機能
   - 運営画面から、**有料ユーザーを無料ユーザーへ変更（強制降格）できる**。
   - **当面の対象は Cat Key 利用者のみ**（2026-06-03 方針: 「今は Cat Key のユーザーだけで大丈夫」）。Cat Key の不正利用・退会判明時に運営が手動で降格する。
   - 復元（free → pro 戻し）も可能。「承認する／降格する」の両方を運営が操作できる。
   - （将来）Square 決済など Cat Key 以外で Pro になったユーザーの降格にも広げる場合は、課金（サブスク解約）との整合を考慮する。**現時点では不要**。
4. **監査ログ**
   - 適用・取消・無効コードなどを記録（`cat_key_events`）。
5. **運営者管理**（決定 2026-06-04・独立画面 `/operators.html`）
   - 運営者アカウントの **一覧・追加・削除** を専用画面（`/operators.html`）で行う。
   - 運営者は **ユーザー（`owners`）とは別テーブル `operators`** で管理する（メール・名前・有効フラグ）。一般ユーザー登録を持つ必要はない。
   - **認証は共有管理キー（`ADMIN_SECRET`）を継続**するが、入力は **専用ログイン画面 `/operator-login.html`（画面#11）** で行い、**運営専用セッション `kimaru_admin_session`** を発行する。`operators` は運営者の登録情報・監査ログの実行者表示に用いる（将来、運営者ごとのメール+パスワード `operators.password_hash` ログインへ拡張）。
   - **ユーザー認証（`/login.html`・`kimaru_session`）とは完全分離**。運営画面は `kimaru_admin_session` で保護し、無ければ `/operator-login.html` へ（[screen-flow.md](../screen-flow.md) §6）。
6. **分析ダッシュボード**（`/analytics.html`・#343・決定33）
   - 経営判断と機能改善の優先順位づけに使う数字を1画面に。**北極星は「今月 日程が決まった数」＋「決まったアカウント数」**（登録数やMRRより先に見る）。
   - タブは5つで、並びは「知る → 登録する → 使い始める → 使い続ける → 払う」という道筋そのもの。
     - **サマリー**: 北極星と全体の累計（期間では絞らない＝期間タブを隠す）、月次の推移。率は**売上ベースの「課金転換率」**を出し、プランベースの数は「有料ユーザー」の内訳に置く（#349）。**2026-08-31（#355）に全体像が1画面で読める形へ作り直した**（下記）。
     - **獲得**: 登録数、LP→料金→登録画面→登録完了のファネル、**流入元ごとの登録数**（`owners.signup_source`・#342）、登録画面からの完了率。**2026-08-31（#355）に読み方を整理した**（下記）。
     - **定着**: 【立ち上がり】セットアップ到達率／**初回予約までの日数**／**予約0のアカウント名簿**（止まっている段つき）。【継続】**週ごとのアクティブ**／**30日動きなし の名簿**／2回目が入った割合。
     - **収益**: 課金内訳・**有料プランの出どころ**（プラン × 課金 / Cat Key無償 / 運営付与・#349）・登録→課金までの日数・解約・**有料の壁に当たった回数**（機能別・当時のプラン別／#342）・登録月コホート別の転換率。
     - **機能**: 機能ごとの採用率、画面別PV/UU、画面×プラン、ゲストの予約ファネル、端末、閲覧の流入元。
#### サマリーの構成（#355・2026-08-31）

「いま何を見ればいいか分からない」への対応。**数字は8枚のタイル、内訳はドーナツ、時間の変化は折れ線と棒**、と形で役割を分ける。

| 段 | 中身 | 決めたこと |
|---|---|---|
| 北極星 | 今月 日程が決まった数＋決まったアカウント＋前月比 | この画面でいちばん大きい数字は1つだけ |
| 主要数値（8枚・4×2） | 登録ユーザー／有料ユーザー／課金転換率／MRR概算 ／ 初期設定が未完了／4画面のアクセス（直近30日）／予約の累計／承認待ちCat Key | 並びは **人 → 使われ方 → 運営の宿題**。列数は固定（`auto-fit` だと幅しだいで1行7枚などに割れ、この並びの意味が消える） |
| 内訳・推移 | プランの構成（ドーナツ）／初期設定の進み具合（ドーナツ）／画面のアクセス（4画面の横棒・直近30日） | ドーナツは正方形・横棒は横長で必要な幅が違うので、3等分にはしない |
| 月次 | 日程が決まった数／登録数（棒・直近12ヶ月） | 従来どおり |
| 初期設定で止まっている段 | カレンダー未連携／プロフィール未入力／予約ページ未作成 の人数（横棒・母数は稼働中） | 1人が複数の段で止まるので、合計は「未完了の人数」と一致しない（画面に明記） |

- **初期設定の判定は、ダッシュボードの初期設定カード（[31](./31-onboarding-guide.md)・#353）とまったく同じ3ステップ**。ユーザーの画面では完了なのに運営の画面では未完了、という食い違いを作らないため、条件を増やさない（受付時間はカードに無いので、ここでも見ない）。プロフィールは `owners` の列ではなく `profiles.data`(jsonb)（`bio` のJSON文字列に入る環境もある）。
- **画面のアクセスだけは期間ボタンと無関係に「直近30日」で固定**。サマリーは期間タブを隠しているビューなので、期間の選択で数字が動くと読み違える。前30日と比べるため、`page_events_daily` は最低60日ぶん引いてから期間ぶんに絞り直す。
- **サマリーのアクセスは全画面の合計ではなく、予約の前後で使う4画面に絞る**（2026-08-31・#355）。見たいのは「予約が入る前（検討）と入った後（準備）に、キマルの画面が実際に使われているか」で、全画面の合計はLPとゲストが見る予約ページで大半が埋まり、それが読めないため。

  | 段 | 画面 | パス |
  |---|---|---|
  | 予約の前 | トップ | `/index.html`（旧LPの `/landing3.html` も合算） |
  | 予約の前 | プラン比較 | `/plan.html` |
  | 予約の後 | 相手管理 | `/contacts.html` |
  | 予約の後 | 事前の情報確認 | `/meeting.html`（相手の詳細）・`/answers.html`（事前アンケート回答） |

  画面の一覧は `usage-summary.js` の `SUMMARY_PAGE_GROUPS` が唯一の出どころ（画面側でパスを足すと、タイルの合計と棒の合計がずれる）。パスは `_lib/analytics.js` の `normalizePath` を通した後の形で書く。棒は**いちばん多い画面を100%とした比**（ファネルではないので先頭基準にしない）。全画面の合計はタイルの説明に併記して残す（4画面だけを見ている、と分かるようにするため）。
- 増減は **▲▼± の記号つき**で出す（色だけに意味を持たせない）。増減の善し悪しは指標で逆になるので、向きだけを示し、良し悪しの色は付けない。

#### 数字の名前の付け方（#355・2026-09-01）

「メール確認済み 14.3%」のように**主語の抜けたタイトル**だと、何を数えた数字か画面だけでは分からない。以下を全タブのタイトル・説明・単位にそろえる。

- **タイトルに主語（誰の・何の）と期間を入れる**。「登録ユーザー」→「登録アカウント（累計）」、「予約の累計」→「登録された予約（累計）」、「メール確認済み」→「メール確認リンクを踏んだアカウント（累計）」。期間はサマリー＝`累計`／`直近30日`、ほかのタブ＝`直近N日` か `選んだ期間`（期間ボタンで変わる文言を固定値で書かない）。
- **数字の下（`sub`）に必ず分母を書く**。「稼働中 401件のうち」「登録 412件のうち 21件」。率だけを置かない。
- **単位は 件＝アカウント／回＝画面の表示数（PV）／人（延べ）＝日ごとに重複を除いた訪問者の合計**。画面上部に凡例（`#unit-legend`）を1か所だけ置き、各タイトルでは単位を言い直さない。
- **対象外があるなら書く**。メール確認は Googleログインで登録した人に確認メールを送っていないので対象外、有料プランの割合は Cat Key など無償の付与を含む、など。
- **表の見出しにも単位を入れる**（「表示数（回）」「訪問者数（人・延べ）」「使ったアカウント（件）」）。
- 実装と名前を必ず突き合わせる。コホートの `rate` は `paid / signups`（無償の付与を含む）なので、列名は「有料プランの割合」で、「課金転換率」ではない。

#### 獲得タブの読み方（#355・2026-08-31）

- **ファネルの右の数字は「前の段からの通過率」**。先頭からの到達率は棒の長さがすでに表しているので、数字にすると同じことを2回言うだけで、**どの段で落ちたか**が読めなかった。段ごとの率だけでは全体が出ないので、下に「先頭の段 → 最後の段（通過率）」の1行を添える。
- **通過率を出さない場合がある**。前の段が0回のとき（計測が薄い）と、後の段が前の段より多いとき（登録完了だけは実データなので、Google認証など登録画面を通らない経路で起こる）は `—` にする。0で割った数字や100%超えを出すと、ファネルが壊れているように見える。理由は `title` で出す。
- **流入元は表ではなく横棒**。流入元は数行しか無いことが多く、表だと1行だけが広い枠に浮いて読めなかった。棒はいちばん多い流入元を100%とした長さ、右の小さい数字は登録数に占める割合。
- **出せない数字は「—」だけで終わらせない**（「登録画面の表示が0回のため出せません」まで書く）。
- **全幅の枠に置くグラフは `barChart`/`lineChart` に広い `width`（viewBox）を渡す**。svg は `width:100%` なので、既定の720のままだと高さが枠の半分近くまで伸び、数本の棒のために1画面ぶんの余白ができる。枠の実幅（`clientWidth`）で 720 / 1200 を選ぶ。

   - 取得できなかった表は0ではなく「取得不可 / 計測待ち」として出す（0で見せると「使われていない」と読み違えるため）。休眠は足あと（`page_events`）が無い環境では数えない。
   - サイドメニューは3画面共通（`public/operator-nav.js` が単一ソース）。分析ダッシュボードだけアコーディオンで5つの子ビューを出し、別画面からでも目的のビューへ直接飛べる。
