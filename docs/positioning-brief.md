# ポジショニング・ブリーフ（新LP用）— キマル

- 作成: 2026-09-01（#362）
- 目的: 新しいURLで作るLPの前提を1本に固定する。**このドキュメントはコピーと構成の根拠であって、LPそのものではない。**
- **LPの方針: 競合比較のLPは作らない。** キマルだけの強みを単独で言い切る。競合データは**裏で使うフィルター**であって、LPに出すものではない。
  - 使い道1: **言ってはいけない語を決める**（全社が言っている＝選ぶ理由にならない語を排除する。§2.2）
  - 使い道2: **「キマルだけ」と言い切れるかを検証する**（言い切れない主張をLPに載せないため。§2.3・§4.0）
  - **LPに他社名・比較表・「〇〇より」は出さない。**
- **このLPの合否は「見た人のうち何人が会員登録したか」で見る。**滞在時間・PV・SNSの反応は補助。指標の取り方と、新URLに置くときの注意は §6。
- 扱い: 「確定」＝依頼者から与えられた入力／キマルのサイトに書かれている事実／一次ソースを確認した競合の公開情報。「**要確認**」＝当方の仮説・未確定。要確認のままLPの見出しに使わない。

### 2.4 競合が構造的に弱い＝キマルが取れる場所

- **顧客像が違う**。TimeRex／Spir／eeasy／Jicoo の口コミ投稿者は 20〜1000人以上の企業が中心で、機能追加の要望も「ラウンドロビン」「会議室の空き」「複数人の or 条件」「アサインのダッシュボード」＝**チームの調整**。個人事業主が1人で使う場面は各社の主戦場ではない。
- **課金の形が違う**。競合は席課金（¥900〜1,600/人）。キマルはアカウント単位の定額で、無料のままでも Meet 自動発行・リマインド・キャンセル/変更まで実運用できる。

- **聞いた答えの行き先が違う**。予約時の質問はどこにでもあるが、**回答が相手ごとに束ねられ、次に会うときに返ってくる**設計は見つからなかった（§2.3）。

## 4. 確定させたいこと

### 4.0 キマルだけの強み（LPの中核主張・他社に触れずに言い切る形）

> **キマルは、予約を受けるときに聞きたいことを聞けて、その答えが相手ごとに残るツール。会う前に開けば相手のことが分かり、会ったあとのメモも同じ1枚に貯まる。日程を決める作業が、そのまま相手の情報になる。**

**「聞ける」と「管理できる」は1本の線で言う。**別々の機能として並べない——「質問できます」だけなら他にもあり（§2.2）、「管理できます」だけなら CRM と誤解される（§2.3）。**キマルの強みは、聞いた答えが予約フォームの提出物で終わらず、相手の記録として積み上がること。**

**なぜ言い切れるのか（社内向けの根拠。LPには書かない）**

- 単一の機能では言い切れない。**予約時の質問項目**は他にもあり、**名簿・予約履歴**も、**メモ**を持つものもある（§2.2・§2.3）
- 言い切れるのは**つながり方**：
  1. 予約のときに聞く（事前アンケート。無料2問／Pro 5問・選択式）
  2. その回答が**相手ごとに束ねて残る**（予約1件の付属物ではなく、その人の情報として）
  3. 会う前に**返ってくる**（相手の詳細画面・22分前のプロフィール付きリマインド）
  4. 会ったあとの**メモ・印象スコア**が同じ1枚に足される
  5. （近日公開）**自分のAIを繋いで**次の一手を出す＝AI利用料が二重にならない
- 調べた範囲で、**1〜4がひと続きになっているものは見つからなかった**。ただし「世界で唯一」とは書かない。**LPで言い切るのは「キマルはこうである」であって、「他にはない」ではない。**

**この主張を支える証拠（LPに置く順）**
1. **相手の1枚（画面）**— 事前アンケートの回答・メモ・印象が並んでいる実物。**これが主役**
2. 質問を作る画面 — 何を聞くかを自分で決められる（選択式も）
3. 会う前に返ってくる導線 — 22分前のプロフィール付きリマインド／相手の詳細
4. 値ごろ感 — 無料で日程調整は最後まで回り、Pro ¥980 から記録が残り始める
5. （公開後）自分のAI接続

### 4.1 ターゲットの1行定義

> **人と会うことが仕事になっている個人事業主**——初回の面談から関係を積み上げて仕事につなげる人。調整相手は社内の同僚ではなく、**毎回ちがう「はじめて会う相手」**。

- 規模：個人事業主（従業員なし〜数名）
- **「ひとり用」「1対1専用」とは言わない**（将来の方向を狭めるため・§7 の要確認11）。言うのは「個人事業主向け」まで
- 相手：見込み客・紹介された人・クライアント候補（**要確認**：業種によって「候補者」「メンバー」になる）
- **要確認**：業種の第1優先（保険・不動産などの個人営業／コーチ・士業・コンサル／コミュニティ運営 のどれを主戦場にするか）。ここでコピーの語彙が変わる

### 4.2 ターゲットが今抱えている痛み3つ

その人が実際に口にする言い方で書く。**現時点では仮説**（根拠は §3 の企業ユーザーの声とキマルの機能設計。個人事業主本人の言葉での裏取りは §7）。

1. **「この人、前に何を話したんだっけ」**
   会う直前にメールとカレンダーとメモアプリを行き来して、相手のことを思い出そうとしている。
2. **「予約は入るのに、次につながらない」**
   日程は決まる。会えている。それでも一度きりで終わり、何が足りなかったのかも残っていない。
3. **「ツールを増やすほど、記録がバラける」**
   日程調整ツールと顧客管理と手元のメモが別々で、結局どれも中途半端に埋まっている。1人なので、運用ルールを作る相手もいない。

### 4.3 差別化軸（絞る。増やすほど弱くなる）

**軸1：予約のときに「聞ける」——日程調整が情報収集になる**
何を聞くかを自分で決められる（無料2問／Pro 5問・選択式）。相手は予約と同時に答えるので、**別途アンケートを送る手間も、答えてもらえない心配もない**。
※「質問できます」だけでは差にならない（他にもある・§2.2）。**必ず軸2とつなげて言う**——「聞いた答えが、そのまま相手の情報になる」。

**軸2：聞いた答えと会ったあとが、相手ごとに「管理」される**
回答・面談メモ・印象スコアが**相手ごとに1枚**に貯まり、会う前に開けば前回の続きから話せる。予約1件ごとのフォーム提出物ではなく、**その人の情報として積み上がる**のが違い。
※言い方の注意：「CRM」と書かない（§2.3）。案件管理・パイプラインを期待されて機能不足に見える。「相手の記録」「相手の1枚」で言う。

**軸3（条件付き）：AIの利用料を二重に払わない**
プレミアムは自分の ChatGPT / Claude を MCP で接続する方式＝回数無制限、キマル側にAI原価が乗らない。競合が同じ形を取りにくい構造的な差。
**ただし今は「近日公開（フェーズ2）」**。提供中と書けないので、**LPの主張に載せるなら「これから」と明示するか、公開まで軸から外す**。判断は §7。
※LPでの言い方は「他社はAI料金を上乗せする」ではなく「**自分が契約しているAIをそのまま使えるので、AIの料金を二重に払わない**」——主語をキマルとユーザーだけにする。

**採用しない軸**：占いベース相手分析（算命学＋数秘術）。他社に無い＝差別化にはなるが、**個人事業主向けの業務ツールとしての信用を毀損する可能性があり、主軸に置くとターゲットが割れる**。LPでは機能一覧の中に置き、見出しでは使わない（**要確認**：依頼者がこれを主軸にしたい場合は方針変更）。

### 4.4 「キマルは〜ではない」（狙わない領域の明示）

- **法人・チームの調整基盤ではない**。ラウンドロビン、担当者の自動割り当て、会議室の空き、席の一括管理はやらない（**将来やるかは §7 の要確認11**。LPでは「やらない」と書かず、単に触れない）
- **CRM／SFAの代替ではない**。案件管理、パイプライン、売上予測、一斉メール配信は持たない。持つのは「聞いた答えと、会った記録」まで
- **アンケートツールではない**。予約と切り離した単体の調査・回収はしない。聞けるのは**予約のときに、これから会う相手に**
- **集客ツールではない**。予約ページは来た人を受けるためのもので、人を連れてくる機能はない
- **法人の一括導入向けではない**。SSO、監査ログ、IP制限、席の一括管理はやらない
- **「速い・簡単・効率化」を売りにしない**。それは全社が言っていて、選ぶ理由にならない
- **「1対1専用」「ひとり用」と名乗らない**。現在の機能は1対1中心だが、それを看板にすると将来の方向を自分で塞ぐ（§7 の要確認11）

### 4.5 メインコピー案5パターン

いずれも「速い・簡単・効率化」を使っていない。カッコ内はサブコピー案。
**［単独］**＝キマルの話だけで成立する。**［対比］**＝「予約ツール一般」というカテゴリを引き合いに出す（他社名は出さないが、比較の色が出る）。**比較LPにしないなら［単独］を主見出しに使い、［対比］はスクロール後の説明ブロックに回す。**

1. **「日程を決めるついでに、聞いておく。」** ［単独］
   （予約フォームがそのまま事前アンケート。答えは相手ごとに残ります）
2. **「会う前に、相手のことが分かっている。」** ［単独］
   （予約のときに聞いた答えが、当日の画面に並んでいます）
3. **「聞いた答えが、そのまま相手の記録になる。」** ［単独］
   （アンケートの回答も、面談のメモも、印象も、1人ぶん1枚に）
4. **「何を聞くかは、あなたが決める。」** ［単独］
   （予約のときに聞ける質問を自分で作れます。答えは相手ごとに貯まります）
5. **「予約ツールは、予定を残す。キマルは、相手を残す。」** ［対比］
   （聞いた答えも、会ったあとのメモも、相手ごとに1枚に）

※ 1〜4 はキマルの話だけで立つ。5 は「いまのやり方では残らない」という気づきを作る用途なので、主見出しではなく本文の入り口に置く。
※ **推奨は 2 か 3 を主見出し**。2 は「会う前」の得（＝当日の安心）、3 は「聞ける×管理できる」の連結そのもの。1・4 は質問設定に価値を感じる層（士業・コーチ・コンサル）に寄る＝業種確定後に判断。

## 5. LPの構成に落とすときの申し送り

- **数値実績は使えない**（導入社数・調整件数・満足度いずれもサイトに無く、作れない）。数値の代わりに「何が残るか」の画面イメージで見せる
- **比較表は置かない。他社名・「〇〇より」も書かない**（比較LPにしない方針・冒頭参照）。カテゴリとして当たり前の機能（カレンダー連携・URL発行・リマインド）は「できること」の欄に淡々と並べ、**紙面の主役は §4.0 の主張とその証拠（相手の1枚の画面）に割く**
- 「他にはない」「唯一の」と書かない。**書けるのは「キマルはこうである」まで**（§4.0）。言い切れない主張を載せると、1つ反証されただけでLP全体の信用が落ちる
- **出口は登録の1本**（合否が登録転換率なので・§6.5）。料金・機能の詳細への導線は主CTAより下に置く
- プレミアム（AI・MCP）は**「近日公開」と明記**。提供中と読める書き方にしない
- できないこと（複数人の同席調整など）は聞かれたら正直に答える。ただし**「1対1専用」「ひとり用」を売り文句にしない**（§4.4）。書くのは「できること」であって、「やらないこと」の宣言ではない

## 6. このLPの合否をどう測るか（主指標＝会員登録への転換率）

### 6.1 主指標

> **LPを見た人のうち、会員登録まで進んだ割合。**

- 分子：**登録数**（`owners` の実数。計測タグが落ちても正しい）
- 分母：**LPの閲覧**（`page_events` の表示数／訪問者数。#342）
- 補助として：登録画面を開いた人のうち登録した割合（＝LPで納得できたが、フォームで落ちた人が分かる）

### 6.2 いまの仕組みで、どこまで見えるか

運営の分析ダッシュボード（`analytics.html` の「獲得」）に、すでに次が出ている。**新しく作るものは無い。**

- **LP閲覧 → 料金ページ閲覧 → 登録画面を開いた → 登録完了** の段ごとの数と、前の段からの通過率
- **登録画面を開いた人が登録した割合**
- **流入元ごとの登録数**（`owners.signup_source`＝最初の外部リファラのホスト。#342）

### 6.3 新しいURLに置くときの注意（**ここが今回いちばん壊れやすい**）

いまの計測は「kimaru-co.jp のHTMLに Edge Function が `usage.js` を差し込む」仕組み。**別ドメインに置くと、この2つが同時に切れる。**

1. **LPの閲覧が `page_events` に入らない**＝分母が取れない
2. **`owners.signup_source` に流入元が残らない**＝「そのLP経由で何人登録したか」が言えない

対策は3つ。**どれを採るかは着手前に決める（§7 の要確認9）。**

| やり方 | 分母（閲覧） | 流入元の紐付け | 備考 |
|---|---|---|---|
| A. 同じNetlifyサイトの別パス（例 `/lp/…`） | ○ そのまま入る | ○ そのまま | **いちばん確実。**新URLの見た目は自由に作れる |
| B. 別ドメイン＋計測を移植 | ○ `usage.js` を読み込ませる（`/api/usage` はCORS要確認） | △ 登録リンクに `?src=` を付けて運ぶ（Googleは `google-auth-start?src=`、メール登録は本文の `source`。仕組みは既にある） | 実装が要る |
| C. 別ドメイン・計測なし | ✗ 取れない | ✗ | **主指標が測れないので不可** |

**決定（2026-09-01・#364）: A を採用。** 新LPは `public/lp.html`（URL `/lp.html`）に置いた。Edge Function が全HTMLに `usage.js` を差し込むので閲覧は `page_events` にそのまま入り、`/lp.html` は運営の「獲得」タブのLP閲覧（`usage-summary.js` の `acquisition_funnel`）にも合算している。**別ドメインへ移すと分母と流入元が同時に切れる。**

### 6.4 目標値

- **業界平均は手元に無い。数値目標を先に置かない（要確認）。**
- 代わりに、**いまの実測をベースラインにする**：公開前に現行LPの「LP閲覧 → 登録完了」を分析画面から取り、新LPはそれを上回るかどうかで見る。比較対象が自分の過去なら、外の平均値は要らない
- 期間は登録の実数が数十件たまるまで見る（1日単位の上下で判断しない）

### 6.5 転換率を主指標にすることの、コピーへの含意

- 主見出しは**気づきより自分ごと化**が効きやすい。§4.5 の［単独］案（3・5）は「自分の話だ」と思わせる型なので相性がよい。［対比］案（1・2）は気づきは作るが、**行動に近いのは［単独］**
- CTAは**登録の1本**に絞る。いまのトップは「無料で始める」「Proを始める」「AIアシストを見る」「料金・プランを見る」が横並びで、**登録以外の出口が3つある**。新LPでは料金・機能への導線は下に置き、上部のCTAは登録だけにする
- **登録だけ増えて使われないコピーを避ける**ため、副指標として「登録後に初期設定3ステップが終わった割合」を見る（同じ分析画面にある）。ここが落ちるコピーは、期待値を作りすぎている

## 7. 要確認（依頼者への質問）

1. **業種の第1優先**：保険・不動産などの個人営業／コーチ・士業・コンサル／コミュニティ運営・イベント主催 のどれを主戦場にするか。§4.2 の痛みの言い回しと §4.5 のコピーはここで最終決定する
2. **調整相手**：見込み客か、既存クライアントか、候補者か（コピーの主語が変わる）
3. **プレミアム（MCPのAI）の提供時期**：差別化軸3に入れるか、公開まで外すか
4. **占いベース相手分析の扱い**：主軸に置きたいか、機能一覧に留めるか
5. **将来の方向**：ひとりのまま深くやるのか、チームへ広げるのか（§4.6 最後の反論の回答が変わる）
6. **狙わない領域の追認**：§4.4 の6項目でよいか。外したくないものがあるか
7. **個人事業主の生の言葉**：§4.2 の痛みは仮説。既存ユーザー数名へのヒアリング（または問い合わせ・解約理由の記録）で裏が取れると、コピーの精度が上がる
8. **一次資料の活用**：キマルには「無料/Proが上限や有料機能にぶつかった記録」（`page_events` の `limit_hit`・#342）があり、運営の分析画面から見られる。**実際にどの壁にぶつかっているか**が分かれば、痛み2・3の裏付けと価格の説明に使える
9. **新LPの置き場所**：§6.3 の A（同じサイトの別パス）／B（別ドメイン＋計測移植）のどちらにするか。**Cは主指標が測れないので不可**
10. **公開前のベースライン取得**：現行LPの「LP閲覧 → 登録完了」の実測を先に取っておくか（新LPの合否がこの1本で決まる）
11. **1対1以外の方向**：複数人・チームの調整をやる予定があるか。「1対1専用」「ひとり用」を看板にしない方針にしたので、**§4.4 の「法人・チームの調整基盤ではない」も将来と矛盾しないか**の確認が要る（現在の実装は1対1のみ）
12. **質問項目の使われ方**：既存ユーザーが実際に何問・どんな質問を設定しているか。`questionnaire_questions` を見れば分かる。**軸1の説得材料（実例）としてLPに載せられる**（実データの引用可否は要判断）
