# 31. 初期設定の導線と使い方ガイド

対象: 発行者（ホスト）　状態: 実装済み（#353・2026-08-27）

## これは何か

登録直後の「何をすれば動き出すのか分からない」を解く2つの導線。

1. **初期設定カード** — ダッシュボード上部に出る3ステップのチェックリスト（進捗つき）
2. **使い方ガイド** — ヘッダーの「使い方ガイド」から開く、左右に送る紙芝居形式のModal

## なぜ必要か

「初期設定の方法がわかりにくい」というユーザーからの指摘。登録直後のダッシュボードは
「今日の予定（空）」「予約ページを共有（まだ無い）」「要対応」が並ぶだけで、**最初に何を
すればサービスが動き出すのか**が画面から読み取れなかった。

実際に詰まる順番は決まっている。カレンダーが未連携だと空き枠が正しく出ず、予約ページが
無ければ共有するURLも無い。この「使えない理由」が画面のどこにも出ていなかった。

## 1. 初期設定カード（ダッシュボード）

| ステップ | 完了の判定 | 導線 |
|---|---|---|
| ① Googleカレンダーと連携する | `/api/me` の `calendar_connected` | `/api/google-auth-start?connect=1`（設定画面を挟まず直接） |
| ② 予約ページを作る | `/api/booking-pages` の件数 ≥ 1 | `/booking-settings.html?new=1` |
| ③ プロフィールを設定する | `/api/profile` の基本7項目がすべて埋まっている | `/profile.html` |

### 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 達成状況の取得 | **既存の取得を使い回す**（新しいAPIを足さない） | ダッシュボードは既に `me` / `booking-pages` / `profile` を叩いている。カードのために往復を増やさない |
| 判定できないとき | **カードごと出さない**（3つとも判明するまで `hidden`） | 取得に失敗した項目を「未完了」と決めつけると、連携済みの人に「連携する」と出してしまう |
| 強調 | **次にやる1つだけ**を朱のボタンにする | 3つとも同じ強さで並ぶと、どれから手を付けるか分からない |
| ③の基準 | 「要対応」の**プロフィール未設定**と同じ（7項目すべて） | 2か所で基準が違うと「完了なのに要対応に出る」が起きる |
| 完了後 | 完了の行を出し、「閉じる」で以後は出さない（`localStorage: kimaru.setupDone`） | 済んだ人の画面を毎回占有しない。連携解除などで未完了に戻ったら再び出す |
| 保存先 | localStorage（DB列を足さない） | 端末ごとの表示の好みでしかなく、サーバに持つ理由がない |

## 2. 使い方ガイド（機能一覧ページ＋項目ごとの説明Modal）

ヘッダーの「使い方ガイド」は **`/guide.html`（機能一覧）** へ送る。一覧は**文字だけ**（項目名＋1行の要約）で、
選ぶとその項目の説明Modalが開く。現在16項目。

| 章 | 項目 |
|---|---|
| 概要 | キマルとは／予約ページとは |
| 予約受付の準備 | Googleカレンダーの連携方法／Zoomの連携方法／予約ページの作成方法／予約ページの設定項目／受付時間と前後の余白の設定方法／事前アンケートの設定方法／プロフィールの設定方法 |
| 案内から面談当日まで | 予約ページの共有方法／ピンポイント日程調整の使い方／予約確定後の流れ／キャンセル・日程変更への対応 |
| 継続的な利用 | 相手管理とは／相手管理の使い方／プランごとの機能の差異 |

### 説明の中身は項目ごとに形が違う

読み手が知りたいことは項目ごとに違うので、`guide.js` の `ENTRIES` で説明の部品を選ぶ。

| 部品 | 使う場面 | i18n キー |
|---|---|---|
| `lead` | 全項目。1段落の要約。**一覧にもこの文を出す** | `guide.<key>.lead` |
| `points` | 「〜とは」の概要。順序のない箇条書き | `guide.<key>.point1..n` |
| `steps` | 「〜の連携方法」「〜の作成方法」。順序のある手順 | `guide.<key>.step1..n` |
| `fields` | 「〜の設定項目」。欄の名前と説明の対 | `guide.<key>.field1.name` / `.field1.desc` |
| `note` | 上限・できないこと・元に戻せないこと | `guide.<key>.note` |

必要なキーはこの指定から機械的に決まるので、`scripts/test/unit.mjs` が3言語ぶんの有無を確認できる。

### 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 入口 | ヘッダーからは**まず一覧へ**（Modalを直接開かない） | 通しの紙芝居だけでは「予約ページの作り方だけ知りたい」人が目的の1枚に着くまで送り続けることになる。読み物として通しで読みたい人のために、Modal側の「次へ」は一覧の並び順のまま残す |
| 説明の粒度 | **「〜とは（概要）」と「〜の方法（手順）」を別の項目に分ける** | 1項目に概要と手順を同居させると、知りたいほうに辿り着くまで読み飛ばすことになる。「予約ページとは」と「予約ページの作成方法」「予約ページの設定項目」は別々に開ける |
| 説明の型 | **項目ごとに部品を選ぶ**（全項目を同じ型で書かない） | 当初は全項目が「図＋利用場面＋3ステップ」だったが、それでは「Zoomはどう連携するのか」「この欄は何を意味するのか」に答えられなかった |
| 一覧の見せ方 | **項目名だけのボタンを並べる**（要約も出さない） | 項目が16に増えたため、1件あたりを短くして一覧性を優先する。要約（`lead`）はModalの冒頭にだけ出す |
| ボタンの見た目 | 1pxの枠＋角丸6px、**下辺だけ3pxで立体に見せる**（影は使わない） | 押せることを見た目で示す。押したときは下辺を1pxに戻して同じぶん下げる（沈む動きになり、高さは変わらない）。影を足すとカードに見え、`--shadow` を使う既存のカードと区別がつかなくなる |
| 図 | **持たない** | 項目が「機能」から「操作」に細かくなったことで、図が手順の言い換えにしかならなくなった。16枚を保守し続ける理由が無い（`.s-*` のCSSと骨格SVGの生成コードは削除） |
| 置き場所 | **`/guide.html` だけが `guide.js` を読む** | 開く先が一覧1枚に決まったので、全ページに配る必要がなくなった（当初は `usage.js` と同じく Edge Function が全HTMLに注入していた）。他の画面からは共通ヘッダーのリンク＝ただの遷移で足りる |
| 一覧の中身 | `guide.js` の `ENTRIES` / `GROUPS` に持ち、HTMLには項目名を書かない | 項目名を2か所に持つと、説明を1つ足したときに必ず片方が古くなる。`group` の書き忘れと、部品を1つも持たない項目は `scripts/test/unit.mjs` が落とす |
| ログインの要否 | **不要**（`PROTECTED_PATHS` に入れない） | 中身は操作の説明だけで、ユーザーのデータを含まない。登録前に「何ができるのか」を読めるほうがよい。ヘッダーの導線自体は従来どおり `.app-only` |
| 直リンク | 開いている項目を URL の `#key` に載せる（`/guide.html#zoom-connect`） | 案内メールやサポートの返信から、特定の説明へ直接送れるようにする。`pushState` にしないのは、16項目送ったあとの「戻る」が16回ぶん必要になるため |
| 文言の置き場所 | i18n.js（`guide.*` キー・3言語で156キー） | 3言語の対称性を既存のテストで担保できる |
| 文体 | **公的な手引き・外部資料に準じた です・ます調**（「〜のとき。」のような体言止めの断片、「〜だけです」のような口語を使わない） | 当初の文体は語りかけ調で、読み手に「機械が書いた文章」という印象を与えた。手順書として読まれるものなので、条件は「〜する場合」、動作は「〜します／〜できます」で統一する。初期設定カードの説明文も同じ文体に揃えた（隣り合う2画面で語り口が変わると、同じ製品の説明に見えない） |
| ナビの折り返し | ログイン時だけ**ハンバーガーの境界を1180pxに広げる** | ナビが10項目になり、1180px 未満では言語選択とアバターが2段目に落ちてヘッダーからはみ出す（従来も1024px以下で起きていた）。未ログインは3項目なので900pxのまま |

## 残る穴

- どの機能を開いたか・どの枚で離脱したかは計測していない（`page_events` の `event` は
  `page_view` / `limit_hit` の許可リスト制。増やすならサーバ側の許可リストも触る必要がある）。
  一覧ページ自体の表示回数は `/guide.html` の `page_view` として残る。
- 一覧に検索・絞り込みは無い（16項目・4章なのでスクロールで足りる）。項目が増えたら検索を足すかを決め直す。
- 説明はすべて手書きで、画面の実装とは自動で同期しない（例: `bs.*` の文言を変えても `guide.page-settings.*` は変わらない）。
  設定項目を増減したときは、この2つを合わせて直すこと。
- ステップ②は「予約ページが1枚でもある」だけを見ており、受付時間が空のままでも完了になる。
