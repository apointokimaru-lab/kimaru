# 30. ピンポイント日程調整（/p/ リンク）

対象: 発行者（ホスト）／ゲスト　状態: 実装済み（#303）

## これは何か

通常の予約ページ（`/b/<slug>`）は「受付時間の空き枠すべて」をゲストに見せる。
ピンポイント日程調整は、ホストが**あらかじめ選んだ数枠だけ**を提示する専用リンク。

「この3つのどれかでいかがですか」と個別に打診したいときに使う。ゲストはカレンダーを
操作せず、提示された候補から1つ選ぶだけで済む。

## 決定事項（#303）

| 項目 | 決定 | 理由 |
|---|---|---|
| リンクの使い切り | **何人でも使える**（候補が埋まるまで有効） | 同じ候補を複数人に打診する使い方を想定 |
| 候補枠の確保 | **一度非表示・再設計待ち**（2026-08-13・#319）。当面すべて先着順 | 予約成立時に押さえが解除されず、外す画面も無かった（下記「枠の確保」参照） |
| 候補の選択元 | キマルが算出した空き枠のみ | 受付時間・前後バッファ・Googleカレンダーとの整合を崩さない |
| リンク管理画面 | 今回は作らない | 発行直後にURLをコピーできれば運用は回る。必要になってから追加する |
| 配信範囲 | **当面プレミアム限定**（2026-08-13） | まず限定配信して使われ方を見る。恒久的な決定ではない |

## プラン

**リンクの発行はプレミアムのみ。** 無料・Pro には予約ページ一覧の「ピンポイントリンク」ボタン自体を出さない
（`app.js` `renderBookingPages`）。サーバ側も `pinpoint-create.js` が `requirePremiumOwner` で 403 にする。

**ゲスト側（`/p/<token>`）はプランで絞らない。** 絞ると、発行者がプランを下げただけで**すでに相手に
送ったリンクが切れる**。約束を反故にすることになるので、発行済みリンクは開けるままにする
（他のプラン変更と同じ grandfathering の方針）。

## URL

`/p/<token>` → `booking.html`（`netlify.toml` の rewrite。`/b/*` と同じページを使い、
`booking-week.js` が token の有無でピンポイント表示に切り替える）。
token は推測されないランダム文字列。slug と違い、URLを知っている人だけが開ける。

## データ

`pinpoint_links`（`supabase-schema.sql`）

| 列 | 意味 |
|---|---|
| `token` | URLの `/p/<token>`。一意 |
| `booking_page_id` | どの予約ページの設定（所要・バッファ・質問・開催方法）を使うか |
| `slots` | 発行時に選んだ候補枠のスナップショット `[{start, end}, ...]`（ISO8601・UTC） |
| `hold_slots` | true なら、この候補枠を通常の予約ページからも埋められないよう押さえる |
| `is_active` | 発行者が止めたときに false |

候補は**スナップショットで持つ**。受付時間や所要時間を後から変えても、打診済みの候補は
変わらないほうが約束として正しいため。

## 枠の確保（`hold_slots`）— **現在は停止中（#319）**

> **2026-08-13: 「候補の枠を押さえる」は一度非表示にした。** 設計をやり直してから改めて入れる。
>
> 止めた理由は、運用に入れる前に決めるべき穴が2つあったため:
> 1. **予約が成立しても押さえが解除されない。** `book.js` はリンクを候補の検証にしか使っておらず、
>    成立後に閉じる処理が無い。3枠押さえて1枠が埋まっても、残り2枠は通常の予約ページから消えたまま
> 2. **外す画面が無い。** リンク管理画面が未実装で、解除は `is_active` を SQL で false にするしかない
>
> 停止のかけ方（再開するときはこの3か所を戻す）:
> - `_lib/pinpoint.js` の `HOLD_ENABLED = false` — `heldBusyFor()` が常に空を返す。
>   **画面を隠すだけにしないのは、発行済みリンクが塞ぎ続けるのを止めるため**
> - `pinpoint-create.js` — `hold_slots` を body から読まず false 固定（直接POST対策）
> - `booking-settings.html` の `#pp-hold-field` を `hidden`（DOM には残す）
>
> DB列 `pinpoint_links.hold_slots` と i18n キー `pin.hold*` は残してある。

以下は停止前の挙動（再開時の仕様）。

`hold_slots = true` のリンクの候補枠は、空き枠計算の busy に加える
（`_lib/availability-core.js`）。これにより通常の予約ページからは選べなくなる。

**自分自身の候補は押さえない。** `/p/<token>` を開いたゲストには、そのリンクの候補が
そのまま出る必要があるため、busy を組むときは「自分以外の hold リンク」だけを対象にする。

候補は日時が過ぎれば自然に無効化されるので、有効期限は設けていない。

## 予約成立

ゲストの予約は既存の `book.js` を通す。`pinpoint_token` を受け取ったときだけ、
**選ばれた開始時刻がそのリンクの候補に含まれるか**をサーバ側で検証する。
候補外の時刻をPOSTされても成立させない。

リンクは何人でも使えるため、候補のうち既に埋まったものは
ゲスト側の一覧から除く（表示時に空き枠計算で突き合わせる）。

## 画面

- **ホスト**: 予約ページ一覧の「URLをコピー」の隣に「ピンポイントリンク」ボタン。押すと
  一覧・編集と同じ全幅の**候補選択画面**に切り替わる（`booking-settings.html` の `#pinpoint-view`／
  `app.js` の `openPinpointView`）。
  画面は**ゲストの予約画面と同じ5日タイムグリッド**（`week-grid.js` を共用。前後5日送り・
  範囲ボタンから月カレンダー）で、**枠を押すと候補に入り、もう一度押すと外れる**。
  選んだ枠は白抜き→朱ベタ＋✓に反転し、下のトレイに時刻順のチップとして並ぶ（✕で取り消せる）。
  枠の押さえ方は他の設定と同じ**プルダウン**（押さえない＝先着順／押さえる＝他の予約を入れない）。
  発行するとURLが出るのでコピーして相手に送る。選択は日を送っても保持される。

  グリッドの描画は `public/week-grid.js`（`window.KimaruWeekGrid.render`）に切り出し、
  ゲストの `booking-week.js` と共用している。**選択の意味だけ**が違う（予約＝1つ選ぶ／
  候補選択＝複数トグル）ので、`isSelected` / `onPick` / `picker` で呼び出し側が決める。
- **ゲスト**: `/p/<token>` は **`booking.html` を再利用する**（`netlify.toml` の rewrite）。
  `booking-week.js` がパスからトークンを読み、週表・月カレンダーを隠して候補をラジオ一覧で出す
  （「2026年8月20日（木）14:00〜14:30」形式・`fmtSlotRange`）。
  選ぶと通常の予約と同じフォームが現れ、質問・確認・完了はそのまま既存フローを通る。
  予約時は `pinpoint_token` を載せ、サーバ側で候補内かを再検証する。

専用HTMLを作らず `booking.html` を再利用したのは、質問・確認・完了の画面とロジックを
二重に持つと、片方だけ直して食い違う事故が起きるため。差し替えるのは候補の出し方だけにした。
