## 0. 開発実行環境

実装・リファクタリング・Terraform・テスト作成は、**Claude Code を主要な開発支援ツールとして利用する前提**とする。

- Claude Code がリポジトリ全体を参照できるモノレポ構成にする
- 仕様書、ADR、イベントスキーマ、DBマイグレーションをリポジトリ内で管理する
- 変更は Git ブランチ、Pull Request、CI を通して反映する
- AI 生成コードも、人間によるレビューと自動テストを必須とする
- 実装指示では、対象ファイル、受け入れ条件、禁止事項を明記する

### シークレットの取り扱い

✅ **決定済み（2026-08-06）**: 当初は「調査目的の読み取りは許容」としていたが、範囲が広すぎるため次のとおり改めた（Codex レビュー指摘を採用）。詳細は [`system-spec.md`](./system-spec.md) SEC-5.4。

| 行為 | 可否 |
|---|---|
| 本番シークレットの**生値をモデルの文脈・標準出力・ログへ出す** | **禁止** |
| **参照名による実行**（`$VAR` 等で値を渡し、値そのものは表示しない） | **許容** |
| 実行結果をマスクして表示する（長さ・形式・一致/不一致など） | **許容** |
| 開発・検証での**非本番ダミーシークレット**の使用 | **原則こちらを使う** |
| コード・コミット・ドキュメントへの埋め込み | **禁止** |
| 本番への書き込み操作（env 変更・デプロイ・DB更新） | **明示指示があるときのみ** |
| commit / PR 作成 / マージ | **明示指示があるときのみ** |

**例外（break-glass）**: 生値の確認が避けられない場合のみ、①事前に理由を記録 ②実施後に当該シークレットをローテーション ③監査ログに残す、の3点を必須とする。

## 2. 判断が分かれた点：DB は **Supabase を正式採用**

仕様書は RDS for PostgreSQL を推奨しているが、**現行の Supabase（PostgreSQL）を継続**する。

**これは暫定措置ではなく正式採用**とする。「いずれ RDS へ移す」と決めつけない。性能・セキュリティ・費用の条件を満たす限り継続してよい。移行は下記の再評価トリガーが成立した時点で判断する。

### 先に撤回する論拠

「移行リスクが大きいから継続」は**この規模では成り立たない**。本番は予約93件・オーナー数十件規模で、`pg_dump`/`restore` で完了する。移行の技術的難度は低い。

### 継続する理由

**(1) 並行稼働がそのまま可能になる（最大の理由）**

新旧アプリが同じ DB を参照できるため、画面・機能単位で順に切り替えられ、問題が出れば戻せる。
RDS へ同時に移すと**アプリ移行と DB 移行を同時に行う**ことになり、障害時に原因を切り分けにくい。

```text
現行アプリ ＋ Supabase
    ↓
新アプリ ＋ Supabase（並行稼働）
    ↓
新アプリへカットオーバー
    ↓
安定稼働
    ↓
必要性が出た時点で RDS を再検討
```

**(2) PoC の AWS 構成を単純化できる**

DB が VPC 外なら、**プライベートデータサブネット・NAT Gateway・VPCエンドポイントを PoC で建てずに済む**。

**(3) 後から移す選択肢が安く残る**

データ規模が小さい＝いつ移しても安い。今移す緊急性がない。

### RDS へ移す再評価トリガー

- 法人契約で「VPC 内完結」「AWS 内でのデータ保持」を要求された
- Bot／ワーカーからの接続レイテンシが**実測で**問題になった
- Supabase のプラン費用が RDS 相当構成を上回った
- 監査要件で CloudWatch / IAM への統一が必要になった

### 接続方式は用途で分ける

| 処理 | 接続方式 |
|---|---|
| API・短い CRUD | Supavisor **transaction mode** |
| Bot の短い状態更新 | transaction mode |
| マイグレーション | **direct または session mode** |
| `pg_dump` / `restore` | direct または session mode |
| 長時間トランザクション | direct または session mode |
| session-level advisory lock | **使用しない**（4章） |

- Fargate タスクは増減するため、直結でコネクションを食い潰さないこと。
- **transaction mode では prepared statement の扱いに制約がある**。Drizzle のドライバー設定と PostgreSQL クライアントの組み合わせを**実機で確認**する（PoC の第1週タスク）。

### 移行前に確認すること（費用比較に含める）

仕様書16は「日次バックアップ・PITR・7〜30日保持・月1回の復元試験」を求めている。**Supabase の PITR は上位プラン／有料アドオン**なので、要件を満たすプラン費用を確認し、RDS 相当構成との比較に含める。ここを外すと「安いから継続」の判断が崩れる。

## 3. PoC で削るもの（固定費と運用対象）

仕様書 Stage 1 の月額目安は 3万〜10万円。**PoC は運営者限定（同時Bot 1〜3）**であり、先行100名でも売上は月 ¥98,000 なので、この段階の固定費は絞る。

| 仕様書の構成 | PoC での提案 | 理由 |
|---|---|---|
| ElastiCache (Valkey/Redis) | **入れない**。同時実行制御は4章の方式 | 仕様書自身が「Redis は正本キューにしない／役割はロック・カウンタ・レート制限」としている。同時Bot 10以下ならその役割は DB で足りる |
| NAT Gateway＋プライベートサブネット | **パブリックIP付き Fargate** | Bot はどのみち外向き通信が必要。NAT は固定費＋データ処理料が効く |
| ALB | **置かない**（下記のとおり理由を正確に） | |
| GPU ワーカー（STT） | **CPU の faster-whisper から実測し、必要時のみ自前GPUを比較** | 外部STT API は原価上の理由から常用しない（5章） |
| RDS Multi-AZ | Stage 3 以降 | |

### ALB を置かない理由（記述の訂正）

「API が1タスクだから不要」ではなく、**PoC では公開 API を新設せず、現行 API から AWS サービス（SQS・Scheduler・S3）を操作するため不要**、が正確。

新しい API を Fargate へ移した時点で、**ALB / API Gateway / CloudFront＋Lambda のいずれかが必要**になる。ここを「後で足す」前提として明示しておく。

### パブリックIP付き Fargate のセキュリティ条件

- インバウンドルールなし（アウトバウンドのみ許可）
- コンテナへ SSH 不可・**ECS Exec は通常無効**
- Bot ごとに短期認証情報のみ渡す
- ログは CloudWatch へ送出

### 最初から入れる（後付けが高い）

SQS＋DLQ／EventBridge Scheduler／S3／ECR／Secrets Manager／Terraform／構造化ログ＋Sentry／`tenant_id`／マイグレーション／**主要な外部依存のインターフェース設計**（STT・LLM・Queue・Storage・同時実行制御）。

## 4. 同時実行制御

> **初版の誤り**: 「同時実行制御は Postgres の advisory lock で代替」とだけ書いていた。
> **Supavisor の transaction pooling ではリクエスト間で同じ物理接続が保証されない**ため、セッションレベルの `pg_advisory_lock` は成立しない（セッション終了まで保持される前提が崩れる）。**セッションレベルのロックは使わない。**

### 用途ごとの方式

| 制御対象 | PoC での方式 |
|---|---|
| 短い DB 処理の排他 | **`pg_try_advisory_xact_lock()` を同一トランザクション内で**使う（トランザクション終了で自動解放） |
| 二重 Bot 起動の防止 | **DB の一意制約** |
| 1ユーザー1Bot（長時間） | **`bot_leases` テーブルによるリース方式**（DB 接続を保持しない） |
| ジョブの重複防止 | SQS メッセージ＋**DB の冪等キー** |

### `bot_leases`

```text
bot_leases
- lease_key        （例: tenant_id + user_id）
- tenant_id
- user_id
- meeting_id
- acquired_at
- expires_at
- heartbeat_at
- status
```

- 取得は一意制約で原子的に行う（`INSERT ... ON CONFLICT DO NOTHING`）
- Bot 稼働中は定期的に `heartbeat_at` を更新する（**初期値30秒間隔**）
- `expires_at` は**現在時刻＋2〜5分の短いTTL**とし、heartbeat のたびに延長する
- **予定終了時刻では Bot を停止しない**（会議が延びても切らない）
- **期限切れリースを回収するクリーンアップジョブ**を回す
- Bot がクラッシュしてもリースが残り続けないこと（回収されること）を PoC で確認する

### 補足：SQS メッセージの寿命に Bot 実行を紐づけない

Bot は ECS タスクとして長時間動くが、**その間 SQS メッセージを保持しない**。オーケストレーターは `RunTask` を発行した時点でメッセージを削除し、以降の Bot の状態はイベント（`bot.joined` / `bot.completed` 等）で受け取る。可視性タイムアウトを会議時間に合わせる設計にはしない。

### インターフェースを最初から切る

Redis を後から入れられるよう、実装は抽象越しに呼ぶ。

```ts
interface ConcurrencyLimiter {
  acquire(key: string, ttlSeconds: number): Promise<boolean>;
  heartbeat(key: string, ttlSeconds: number): Promise<void>;
  release(key: string): Promise<void>;
}
```

PoC は PostgreSQL 実装、拡大時に Redis 実装へ差し替える。

### Redis を入れる条件

同時Bot 数十以上／高頻度のレート制限が必要／DB への同時接続制御が負荷になった／分散キャッシュが必要／リアルタイム状態表示が増えた。

### 値上げの発動条件

Proとプレミアムを合算した**課金対象アクティブユーザー数が100人に到達した時点**で、以後の新規契約へ新価格を適用する。

- 先着100人の契約価格は変更しない
- **101人目以降**の新規契約から、Pro ¥2,200、プレミアム ¥4,800 を適用する
- Proとプレミアムを合算して100人を判定する
- **「猫のキー」で Pro を利用しているユーザーは人数に含めない**
- 無料ユーザー、解約済み、支払い停止中のユーザーは含めない
- マスタープランは100人判定の対象外とする
- 100人到達後に人数が100人未満へ減っても、新規契約価格は元へ戻さない

### 課金対象アクティブユーザーの定義

```text
課金対象アクティブユーザー
= plan IN ('pro', 'premium')
  AND subscription_status = 'active'
  AND payment_entitlement = 'paid'
  AND entitlement_source != 'cat_key'
```

「猫のキー」は表示名だけで判定せず、DB 上に機械判定可能な属性を持たせる。

```text
entitlement_source:
- paid
- cat_key
- admin_grant
- campaign
```

推奨する集計値：

```text
pricing_threshold_reached_at
pricing_threshold_user_id
pricing_threshold_count = 100
```

100人目の契約確定時に到達日時を永続化し、以後は現在人数を毎回数えて価格を戻す方式にしない。

**現行実装との対応**: Cat Key は現在 `owners.cat_key_pending` / `owners.cat_key_disabled` で管理している。移行時に `entitlement_source` への**マッピング規則を決める**こと。

### 先行価格ユーザーの識別

契約レコードに価格世代を保存する。

```text
price_generation:
- founding_100
- standard_after_100
```

または、契約時の実価格を保存する。

```text
contracted_monthly_price
price_id
price_effective_at
```

これにより、Square 側の価格変更後も先行100人の金額を維持できる。

**現行実装への影響**: `square-checkout.js` は `SQUARE_PRO_PLAN_ID` を1つしか参照していない。100人到達後は**新プランIDへ切り替え、既存契約者は旧プランのまま**にする必要があるため、新旧プランIDを併存させる実装が要る。

- 先行100人が解約後に再契約した場合、先行価格へ戻れるか

### STT方針

**外部文字起こしAPIは、継続原価が高いため常用しない。** PoC で比較する対象は次の2つとする。

1. 自前CPUバッチ
2. 自前GPUバッチ

STT 実装はインターフェース越しにし、CPU から GPU へ差し替え可能にする。

```ts
interface TranscriptionProvider {
  transcribe(input: {
    meetingId: string;
    audioObjectKey: string;
    language?: string;
  }): Promise<TranscriptionResult>;
}
```

初期実装：

```text
FasterWhisperCpuProvider
```

将来候補：

```text
FasterWhisperGpuProvider
```

> ⚠️ **要確認（外部APIの完全除外）**: 改訂版の原文は「外部APIプロバイダーは実装対象に含めない」。原価上、**常用しない**判断には賛成だが、**完全に実装しないと自前STTが停止したときに文字起こしが一切出せない**（GPU枯渇・モデル更新失敗・キュー滞留・PoCで想定速度が出ない、のいずれかは起こりうる）。
>
> 提案: **常用しない緊急フォールバックとして `ExternalApiProvider` の実装だけ残す**（管理者が明示的に切り替えたときのみ使用）。インターフェースは既に切ってあるので実装コストは HTTP 呼び出し1本、原価は使ったときだけ発生する。**この扱いでよいか確認したい。**

| マスター | 100h | 約 **¥2,340** | ¥9,800 | 成立 |

この判定は、決済手数料、Supabase・AWS 固定費、メール、サポート、税金等を含まない。
正確には「**Bot 機能の変動原価上は成立**」という意味である。

**より精緻な試算**（Fargate 単価から積み上げ、決済手数料込み）は [`system-spec.md`](./system-spec.md) 7章を参照。そこでは**外部STT API を使うとマスターの限界利益が14%まで落ち、プレミアム40時間も29%に下がる**ことを示している。**自前STTは選択肢ではなく前提条件**。

### 総原価の式

```text
1会議時間あたり総原価
  = Bot実行費
  + 音声一時保存
  + 自前文字起こし
  + AI要約
  + SQS / Scheduler / ログ
  + 失敗再処理費
```

```text
実効原価 = 正常処理原価 ÷ 正常完了率
```

### 全プラン共通の会議時間・超過ルール

- Pro：月5時間 ／ プレミアム：月40時間 ／ マスター：月100時間
- **全プランで1会議あたりの最大時間は設けない**
- **全プランで同時Botは1台**
- 同一ユーザーの会議が重複した場合、先に確定した会議を優先する
- 同時刻の2件目には Bot を割り当てず、事前に警告する
- 追加同時Bot は初期プランに含めない
- 将来の法人プランまたは追加オプションとして別途検討する

### 月間利用枠を超えた会議

会議開始時点で利用可能時間が1分以上残っている場合、その会議は終了まで Bot を継続する。

```text
会議開始時に残り時間がある
↓
Botを起動
↓
会議中に月間利用枠へ到達
↓
Botは途中退出しない
↓
会議終了後に超過分をマイナス残高として記録
↓
翌月以降の利用可能時間から自動控除
```

#### 例：Pro

```text
当月残り：30分
会議時間：60分
超過：30分

翌月付与：300分
前月超過：-30分
翌月利用可能：270分（4時間30分）
```

> ⚠️ **要確認（マイナス残高の回収可能性）**: 「開始時に残高1分以上なら最後まで継続」＋「1会議の最大時間なし」＋「超過は翌月控除」の組み合わせは、**Pro（枠5時間）のユーザーが1回の会議で枠を大きく超えられる**設計になっている。翌月控除は契約継続が前提のため、**そこで解約されると回収手段がない**（未決定 #18）。
>
> 提案: (a) 内部安全タイムアウトを短めに設定する（下記の要確認とセット）、(b) 残高が枠の一定割合を切った状態で会議を開始する場合は**開始前に警告を出す**（Bot は起動する）。**この2点を入れるか確認したい。**

### Bot起動可否

| 状態 | 動作 |
|---|---|
| 利用残高が1分以上 | Bot を起動できる |
| 会議中に残高が0以下 | 途中退出しない |
| 会議終了後にマイナス残高 | 翌月以降へ繰り越す |
| 利用残高が0分以下 | 新しい Bot は起動しない |
| 翌月付与後にプラスへ復帰 | Bot を再び起動できる |
| 追加時間を購入 | 購入分を即時加算できる将来拡張を想定 |

### 複数月への超過繰越

1会議の最大時間を設けないため、超過分が翌月の付与時間を上回る可能性がある。

```text
前月残高：-420分
翌月Pro付与：+300分
翌月残高：-120分
```

この場合、翌月は Bot を利用できず、残り120分はさらに翌月へ繰り越す。

### 利用残高の計算

```text
当月利用可能残高
  = 月間付与時間
  + 前月繰越残高
  + 追加購入時間
  - 当月利用時間
```

残高は負数を許可する。

### 利用時間の計測基準

課金対象時間は、原則として Bot が実際に会議へ参加していた時間とする。

| 状態 | 利用時間へ算入 |
|---|---|
| Bot起動準備 | 含めない |
| 会議URLへの接続処理 | 含めない |
| 待機室 | 初期仕様では含めない |
| 会議へ入室後 | 含める |
| 会議中の再接続 | 含める |
| 音声アップロード | 含めない |
| 文字起こし・AI要約 | 含めない |

秒単位で保存し、ユーザー画面では分単位で表示する。

### 内部安全タイムアウト

商品上は1会議の最大時間を設けないが、終了検知失敗による無限稼働を防ぐため、内部安全タイムアウトを持たせる。

- 商品上の利用制限ではなく**異常停止用**
- 到達時は管理者へ即時通知
- 音声は分割アップロードし、取得済み部分を失わない
- 実測後に値を確定する

> ⚠️ **要確認（初期値）**: 改訂版の原文は「初期値候補：12時間または24時間」。**終了検知に失敗した1タスクが最大24時間走ると、Fargate は秒課金なので原価の跳ね方が他と桁違いになる。**1対1の面談で6時間を超えるケースはまず無く、仕様書6章には「無人退出5〜10分」も既にある。
>
> 提案: **初期値を4〜6時間から始め、実測で伸ばす。** 長くするのは後からできるが、暴走した分は取り返せない。**この値でよいか確認したい。**

### 長時間会議の音声処理

- 15分または30分単位で音声を分割
- 各セグメントを順次 S3 へアップロード
- セグメント単位で文字起こし再試行
- 最終的に時系列で統合
- 文字起こし成功後に各音声を削除

### 解約・プラン変更時

次の境界は課金実装前に決める。

- マイナス残高がある状態で解約した場合

- 支払い失敗後に復旧した場合

初期推奨は、超過残高をそのまま維持し、次回付与時間から控除する方式とする。

## 6. 既存本番からの引き継ぎ

仕様書は「これから作るもの」の設計としては十分だが、**稼働中の本番から移る**視点が入っていない。ここを落とすと外部サービスの再申請・再設定が発生する。

| 対象 | 制約 |
|---|---|
| セッションCookie `kimaru_session` | **Cookie 仕様一式と秘密鍵を完全互換で移植すれば、再ログインを回避できる**（下記に現行仕様） |
| Google OAuth redirect URI・スコープ | 変更により**再審査・再検証が必要になる可能性がある**ため、既存設定を維持する（2026-07-11 に `calendar.events` 承認済み） |
| Zoom OAuth redirect URI・スコープ | 同上。**現在審査中**のため、スコープを足す時期に注意。**RTMS のスコープは PoC 用の別アプリで試し（#475）、本番アプリへは #388 を RTMS のスコープで出し直す**（2026-09-05） |
| 予約ページURL `/b/{slug}`・公開プロフィール `/u/{slug}` | 顧客に配布済み。**変更不可** |
| 予約管理リンク `/manage-booking.html?k=<id>.<token>` | 送信済みメールに残る。**旧形式 `?id=&t=` も受け続ける** |
| Square Webhook 受信URL・署名鍵 | 落とすと課金の付与が止まる |
| Resend Webhook（バウンス・苦情の自動サプレッション） | 落とすと配信品質が劣化。`email_suppressions` の移行漏れは法的リスク |
| MCP `/.well-known/*`・`/api/mcp`（OAuth 2.1） | プレミアムの接続が切れる |
| `google_connections` / `zoom_connections` の暗号化トークン | `TOKEN_ENCRYPTION_KEY` の引き継ぎ方針が必要。鍵を変えるなら再暗号化バッチを用意する |

### 現行セッションCookieの完全仕様（新スタックで再現する）

`netlify/functions/_lib/crypto.js` の実装。**Cookie 名と `SESSION_SECRET` だけでは不十分**で、以下すべてが一致して初めて再ログインを回避できる。

```text
Set-Cookie: kimaru_session=<payload>.<signature>; Path=/; HttpOnly; SameSite=Lax; Secure; Max-Age=2592000

payload    = base64url(JSON.stringify({ ownerId, ts }))   ※キーの順序も含めて同一にする
signature  = base64url(HMAC-SHA256(SESSION_SECRET, payload))
Domain     属性なし＝host-only（kimaru-co.jp）
検証       署名を定数時間比較し、さらに ts が 30日以内かつ未来すぎないことを確認
別系統     運営用 kimaru_admin_session が別に存在する（混同しない）
```

移行前に**旧実装が発行した Cookie を新実装で検証できること**をテストで確認する（逆方向も）。

### 追加の確認項目

| 対象 | 確認事項 |
|---|---|
| Cookie | Domain・Path・Secure・SameSite・有効期限・署名形式・payload 形式 |
| HMAC | 旧・新双方で署名検証テスト（相互運用） |
| 時刻 | DB は UTC、UI は JST |
| Cron・予約処理 | 旧新で**二重実行されない**こと（リマインダーが2通行かない） |
| メール | Message-ID・冪等キーによる重複防止 |
| Webhook | 同じイベントを旧新双方で処理しない |
| OAuth state | 新旧で衝突しない |
| CSP・CORS | 新ドメインを許可 |
| DNS TTL | 切替前に短縮 |
| Secrets | 移行後のローテーション計画 |
| Square | Webhook イベントの再送試験 |
| Resend | バウンス・苦情の移行試験 |

## 7. 同一DBでの並行稼働ルール

「同じ Supabase を参照する」は移行を簡単にするが、**旧新が自由に同じテーブルへ書くと壊れる**。次を必須ルールとする。

### Expand – Migrate – Contract

| フェーズ | 内容 |
|---|---|
| **Expand** | 既存を壊さず、新しいカラム・テーブルだけ追加する。**NULL 許容・デフォルト値あり**。旧コードから見ても問題ない状態 |
| **Migrate** | 新旧が共存しながらデータを移す |
| **Contract** | 旧アプリ停止後に、不要カラム・旧仕様を削除する |

### 並行稼働中の禁止事項

- カラム名の変更
- カラムの削除
- 型の変更
- NOT NULL の即時追加
- 旧コードが知らない enum 値の投入
- 既存 API レスポンスの破壊的変更

### 書き込み責任を「データ領域単位」で一つに決める

画面単位ではなくデータ単位で決める。**同一レコードを旧新双方が更新する二重書き込みは避ける。**

| データ | 書き込み担当 |
|---|---|
| 予約 | 旧または新の**どちらか一方**（切替時点を決める） |
| 顧客 | 移行期間中の責任を明記する |
| タスク | 新システムのみ |
| Bot・会議 | 新システムのみ |
| 文字起こし・要約 | 新システムのみ |
| 課金 | **切替完了まで旧システム** |

### `tenant_id` の入れ方

新スタックは全業務テーブルに `tenant_id` を要求するが、現行は `owners` 単位の単一モデル。**Expand フェーズで既存テーブルに `tenant_id` を NULL 許容で追加**し、当面は owner と 1:1 で埋める。テナント＝オーナーのままにするか、`tenants` テーブルを新設して owner を紐づけるかは、法人対応の設計時に決める（未決定 #16）。

```text
旧システムを残す
   ↓

   ↓

   ↓
```

4. 新規予約作成
