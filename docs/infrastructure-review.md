## 1. 同意する点（決着済み）

| 項目 | 採用 | 補足 |
|---|---|---|
| クラウド | **AWS・東京リージョン** | スケール余地と法人向けの説明しやすさを取る |
| Bot 実行 | **ECS Fargate**（1会議1タスク） | 会議時間だけ起動する使い方に合う |

| 言語 | **TypeScript 主軸／文字起こしのみ Python** | 既存ロジック（HMAC・OAuth・各種連携）が JS で移植が最短。Playwright も第一級。faster-whisper 系は Python |
| 構造 | **モジュラーモノリス＋独立ワーカー** | Bot・STT・要約・クリーンアップだけ別プロセス |
| IaC / CI | **Terraform / GitHub Actions** | 現行は CI 無しなのでここで入れる |

### 他候補の検討記録（再検討を避けるため）

| 候補 | 判断 | 根拠 |
|---|---|---|
| 現行 Netlify の継続 | ❌ | Functions は Background でも**最大15分**。120分の会議に滞在する Bot が構造的に不可能 |

## 2. 判断が分かれた点：DB は **Supabase 継続**を推す

仕様書は RDS for PostgreSQL を推奨しているが、**少なくとも移行期〜PoC は現行の Supabase（PostgreSQL）を継続**すべきと考える。

### 先に撤回する論拠

「移行リスクが大きいから継続」は**この規模では成り立たない**。本番は予約93件・オーナー数十件規模で、`pg_dump`/`restore` で完了する。移行の技術的難度は低い。

### それでも継続を推す理由

**(1) 並行稼働がそのまま可能になる（最大の理由）**

移行方式は「並行稼働 → カットオーバー」を採る。DB を据え置けば、**新スタックと現行アプリが同じデータを読み書きしながら共存**できる。画面単位で順に切り替えられ、問題が出れば戻せる。
RDS へ移すと「どの時点でコピーするか」「二重書き込みをどうするか」という移行専用の設計が別途必要になる。

**(2) PoC の AWS 構成を単純化できる**

DB が VPC 外なら、**プライベートデータサブネット・NAT Gateway・VPCエンドポイントを PoC で建てずに済む**。仕様書 25-1 は「PoC ではパブリックIP付き Fargate と NAT を比較する」としているが、DB が外なら比較するまでもなくパブリックIP構成で完結する。固定費と Terraform の管理対象が同時に減る。

**(3) 後から移す選択肢が安く残る**

データ規模が小さい＝**いつ移しても安い**。今移す緊急性がない。

### RDS へ移す再評価トリガー

次のいずれかが立った時点で移行を判断する。

- 法人契約で「VPC 内完結」「AWS 内でのデータ保持」を要求された
- Bot／ワーカーからの接続レイテンシが**実測で**問題になった
- Supabase のプラン費用が RDS 相当構成を上回った
- 監査要件で CloudWatch / IAM への統一が必要になった

### 前提と注意

- リージョンを揃える（Supabase 側も東京）。
- 接続は Supavisor（pgBouncer）経由でプール。Fargate タスクが増減するため、直結でコネクションを食い潰さないこと。
- **アクセス方法は現行から変える**。PostgREST を fetch で叩く方式をやめ、通常の Postgres 接続＋クエリビルダ（Drizzle）＋**マイグレーションツール**にする。現行の「手動で `supabase-schema.sql` を両DBへ適用」は Step 3〜4 のテーブル増加に耐えない。

## 3. PoC で削るもの（固定費と運用対象）

仕様書 Stage 1 の月額目安は 3万〜10万円。**PoC は運営者限定（同時Bot 1〜3）**であり、先行100名でも売上は月 ¥98,000 なので、この段階の固定費は絞る。

| 仕様書の構成 | PoC での提案 | 理由 |
|---|---|---|
| ElastiCache (Valkey/Redis) | **入れない**。同時実行制御は Postgres の advisory lock で代替 | 仕様書自身が「Redis は正本キューにしない／役割はロック・カウンタ・レート制限」としている。同時Bot 10以下ならその役割は Postgres で足りる。固定費と運用対象を1つ削れる |
| NAT Gateway＋プライベートサブネット | **パブリックIP付き Fargate** | Bot はどのみち外向き通信が必要。NAT は固定費＋データ処理料が効く |
| ALB | **PoC では置かない**（API は1タスク） | 台数が増えてから足す |
| GPU ワーカー（STT） | **CPU の faster-whisper から実測** | バッチで遅延許容（会議終了後15分以内）。int8 でリアルタイムの数倍速が出れば CPU で足りる |
| RDS Multi-AZ | Stage 3 以降 | |

**最初から入れる**（後付けが高い）: SQS＋DLQ／EventBridge Scheduler／S3／ECR／Secrets Manager／Terraform／構造化ログ＋Sentry／`tenant_id`／マイグレーション。

## 4. 原価が設計を決める（概算・PoC で要実測）

| 項目 | 1時間あたり概算 | 月30時間枠での1人あたり |
|---|---:|---:|
| Bot コンテナ（2vCPU / 2〜4GB） | ¥3〜15 | ¥90〜450 |
| 文字起こし：外部API（Whisper系） | ¥40〜60 | **¥1,200〜1,800** |
| 文字起こし：自前 CPU バッチ | ¥3〜10 | ¥90〜300 |

> いずれも**概算**。正確な数字は AWS Pricing Calculator と PoC の実測で確定する。

**含意**

- 先行価格 ¥980/月に対し、**外部API方式で月30時間枠を使い切られると単体で赤字**になる。
- 文字起こしは**支配的なコスト**であり、Bot のコンテナ代より桁が大きい。仕様書の「Bot原価15円/時間以下」を達成しても、文字起こしが合わなければ意味がない。
- バッチで遅延を許容できるため、**CPU で faster-whisper を回す構成が現実的な逃げ道**になる。
- 設計としては **STT を差し替え可能なインターフェースにする**（仕様書 29 の「S3・Queue・LLM・STT へインターフェースを設ける」と同じ思想）。まず API 実装で動かし、原価が合わなければ自前 CPU に差し替える。
- 提供時間枠（月30時間／100時間）は、**実測原価が出るまで確定しない**。

## 5. 仕様書に無い観点：既存本番からの引き継ぎ

仕様書は「これから作るもの」の設計としては十分だが、**稼働中の本番から移る**という視点が入っていない。ここを落とすと外部サービスの再申請・再設定が発生する。

| 対象 | 制約 |
|---|---|
| セッションCookie `kimaru_session`（HMAC・30日） | **Cookie 名と `SESSION_SECRET` を維持すれば全ユーザー再ログイン不要**。Auth.js 等に載せ替えると全員が強制ログアウトになる。→ **自前セッションを移植する** |
| Google OAuth redirect URI | 変更すると**再審査**（2026-07-11 承認済みの資産を失う） |
| Zoom OAuth redirect URI・スコープ | 変更・追加は**再審査**。**現在審査中**のため、Bot 用スコープを足す時期に注意 |
| 予約ページURL `/b/{slug}`・公開プロフィール `/u/{slug}` | 顧客に配布済み。**変更不可** |
| 予約管理リンク `/manage-booking.html?k=<id>.<token>` | 送信済みメールに残る。**旧形式 `?id=&t=` も受け続ける** |
| Square Webhook 受信URL・署名鍵 | 落とすと課金の付与が止まる |
| Resend Webhook（バウンス・苦情の自動サプレッション） | 落とすと配信品質が劣化する。`email_suppressions` の移行漏れは法的リスク |
| MCP `/.well-known/*`・`/api/mcp`（OAuth 2.1） | プレミアムの接続が切れる |
| `google_connections` / `zoom_connections` の暗号化トークン | `TOKEN_ENCRYPTION_KEY` の引き継ぎ方針が必要。鍵を変えるなら再暗号化バッチを用意する |

### Bot 対象プラットフォームへの影響

Zoom は審査中で、**Bot 用スコープの追加＝再審査**。審査への影響を避けるなら **Google Meet 先行**が安全。ただし Meet 側にも Bot 参加の規約・技術的可否の確認が要るため、**着手前に両者を調査してから決める**。

## 6. 移行方式

**並行稼働 → カットオーバー**を採る。

1. 新スタックを別ドメイン（例: staging）で立ち上げ、**同じ Supabase を参照**する
2. 画面・機能単位で新スタックへ寄せる（旧はそのまま動く）
3. 外部との約束（5章の表）が新スタックで全て機能することを実機確認
4. DNS を切り替える
5. 問題が出れば旧へ戻す

**本番データのコピーで移行リハーサルを最低1回**行ってから本番切り替えを実施する。

### 完了条件

- 5章の表の項目がすべて新スタックで機能する（実機確認）
- 予約 → 確認メール → リマインド → キャンセル／変更の一連が通る
- ロールバック手順が用意されている

## 8. 最初の一手

PoC で**先に測る**（仕様書 21 の計測項目に原価を足したもの）。

- [ ] Playwright + Chromium で対象プラットフォームへ入室できるか（規約確認込み）
- [ ] 音声のみ取得できるか・欠損率
- [ ] Fargate タスクの1時間あたり実費
- [ ] faster-whisper（CPU int8）のリアルタイム比処理速度と実費
- [ ] 会議終了から文字起こし完成までの実測時間
- [ ] 上記から算出した**1会議時間あたり総原価**

この6つが出れば、提供時間枠・価格・GPU の要否がすべて決まる。
